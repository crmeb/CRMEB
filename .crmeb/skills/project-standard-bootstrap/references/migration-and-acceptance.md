# 迁移与验收

## 已有项目迁移顺序

1. 先审计并冻结事实，不移动目录、不改命令。
2. 建立 `.crmeb/` 真源和根级薄入口，不复制多套规则。
3. 生成 `.crmeb/project.json`，把现有命令映射到统一契约。
4. 补齐 `check/test/build` 门禁，再处理 Docker 和快速启动。
5. 规划 `backend/`、`frontend/` 迁移，逐项更新 import、autoload、workspace、CI、Docker、部署和文档。
6. 目录迁移作为独立变更，运行全量构建、测试和 smoke，并保留回滚点。
7. 最后接入升级包与发布流程，验证旧版到新版链路。

用户只要求文档或规范时，不擅自移动业务代码。无法一次迁移的项目可用兼容入口过渡，但必须记录淘汰计划，避免长期双路径。

## 入口与导航

- [ ] 根 README 能说明项目定位、组成和最短启动路径。
- [ ] 开发、架构、测试、部署和 AI 规则都能从根入口到达。
- [ ] 文档索引按任务组织，没有孤立的关键文档。
- [ ] 内部链接、相对路径和标题锚点全部有效。
- [ ] 后端及每个独立前端应用都有就近 README，并链接到各自的 `help/docs/applications/<应用ID>.md`。

## 事实准确性

- [ ] 语言、框架和工具版本来自 manifest、lockfile、镜像或版本配置。
- [ ] 安装、启动、构建、测试命令在正确目录存在。
- [ ] 端口、路由/API 前缀、模块和数据结构与当前代码一致。
- [ ] 文档明确区分默认值、示例值和环境覆盖值。
- [ ] 待实施方案没有写成已具备能力。
- [ ] 易漂移数字或清单有来源，能自动生成或校验时不靠手工维护。
- [ ] 已逐应用检查 manifest/lockfile、构建配置、入口/路由、环境样例、API 客户端、测试和 CI，并据此更新说明。
- [ ] 本次代码变更影响的应用文档已同步；无需更新的应用已记录检查结论和依据。

## 可运行与可开发

- [ ] 新环境的前置依赖、配置、初始化、启动和成功信号完整。
- [ ] 命令标注执行目录、前置服务和平台限制。
- [ ] 后端业务代码统一位于 `backend/`，没有并列散落的后端业务目录。
- [ ] 每个可独立构建的前端应用位于 `frontend/<应用名>/`，共享包边界明确。
- [ ] 核心目录、模块关系和关键调用链足以支持定位改动。
- [ ] API、数据库、插件/扩展机制等项目关键领域有权威入口。
- [ ] 常见问题包含症状、原因和验证过的处理方式。

## AI 协作

- [ ] `.crmeb/` 是 AI 规则、技能和子智能体的唯一正文来源。
- [ ] 根 AI 入口短小，能指向 `.crmeb/AGENTS.md`。
- [ ] `CLAUDE.md`、`GEMINI.md`、Cursor Rules、Copilot instructions 和 `llms.txt` 都是薄入口，没有复制规则正文。
- [ ] 静态检查确认所有工具入口存在并指向 `.crmeb/AGENTS.md`；已实际验证的工具与仅静态适配的工具分别报告。
- [ ] 规则说明作用域、禁止事项、代码风格和最小验证要求。
- [ ] 子目录有特殊约定时能被 AI 发现。
- [ ] 不同工具入口没有复制多份长期维护正文。
- [ ] AI 能区分正式事实、过程记录和测试说明。

## 前端跨层与 UniApp

- [ ] 前端开发指南能从 API 函数追踪到请求封装、后端路由、业务层、数据访问和迁移。
- [ ] 新字段、列表筛选、表单和权限均有前后端、数据库、测试及升级包同步清单。
- [ ] 文档明确禁止用手工改库替代迁移，也不把前端隐藏控件当作服务端鉴权。
- [ ] 存在 UniApp 时登记真实平台脚本、API 地址链路、认证封装、pages/分包和条件编译约定。
- [ ] UniApp 通用改动至少验证 H5 和目标小程序/App 平台；无法真机验证时明确限制。
- [ ] 升级交付区分 H5 产物、小程序审核、App 资源包和原生安装包。

## Docker 本地开发

- [ ] 已从当前后端的版本、manifest/lockfile、扩展、启动入口和依赖服务生成证据映射。
- [ ] 根 `docker-compose.yml` 已自动生成或按当前环境语义更新，不是未替换的通用模板。
- [ ] `docker-compose.yml`、Dockerfile、工作目录与 `backend/`、`frontend/` 的实际结构一致。
- [ ] 文档列出服务、端口、健康检查、源码挂载、依赖卷和数据卷。
- [ ] 首次启动包含配置、构建、依赖安装、数据库初始化和成功验证。
- [ ] 日常开发包含启动、停止、日志、容器内命令、测试和进程重启。
- [ ] 源码改动能在容器内可见，热更新或需要重启的边界明确。
- [ ] lockfile、Dockerfile 或系统依赖变化后的重建方式明确。
- [ ] `down` 与 `down -v` 的数据影响明确，删除数据卷有显著警告。
- [ ] macOS、Windows、Linux 的监听、权限或架构差异按实际情况说明。
- [ ] 至少执行 `docker compose config`；未构建或未启动时说明原因。

## 测试与验证

- [ ] 测试地图列出层级、目录、命令、依赖和覆盖范围。
- [ ] 文档检查至少覆盖格式、链接和引用路径。
- [ ] 关键事实检查能报告文档值、实际值和证据位置。
- [ ] 实际执行的 lint、测试、构建或运行验证有结果记录。
- [ ] 未执行项及其原因明确，没有夸大验证范围。

## 自动升级包

- [ ] 已定义唯一版本源、目标版本、允许来源版本和版本递增规则。
- [ ] 后端、前端、数据库、配置和插件变更能被正确分类。
- [ ] 核心升级包不混入独立插件/扩展文件，插件包不修改无所有权的核心数据。
- [ ] manifest 包含来源提交、组件、运行要求、迁移、备份、回滚边界和人工步骤。
- [ ] 文件清单和 SHA-256 由构建结果生成并能完整复验。
- [ ] 包内没有 `.env`、密钥、日志、缓存、上传文件、数据库备份或本地运行数据。
- [ ] 数据迁移可追踪、顺序稳定、尽可能幂等，已发布迁移没有被回改。
- [ ] 新安装结果与执行全部存量迁移后的最终结构一致。
- [ ] 所有受影响的前端应用生成发布构建产物，而不是把开发源码冒充线上产物。
- [ ] 至少验证最近稳定版到目标版；声明跨级升级时验证完整迁移链。
- [ ] 失败不会写入成功记录，备份、停止和恢复路径有验证或明确限制。
- [ ] 交付报告包含版本、包路径、来源提交、SHA-256、迁移概要和未验证项。

## 安全与维护

- [ ] 文档和示例不含真实密钥、令牌、Cookie、个人数据或生产地址凭据。
- [ ] 数据迁移、删除、发布、回滚等高风险操作带有边界和前置条件。
- [ ] CI 配置与项目实际托管平台和现有流水线一致。
- [ ] 每类文档有清晰职责和生命周期，不存在重复真相源。
- [ ] 改动未覆盖用户已有修改，`git diff --check` 通过。

## 完成判定

以下条件同时满足才能声明“文档体系已完善”：

1. P0 问题全部解决或明确阻塞；
2. 从零运行、理解架构、修改代码、执行测试四条核心路径都有入口；
3. 关键事实已达到至少静态核对级别；
4. 所有实际验证与未验证项如实报告；
5. 没有为追求目录完整而留下空文档或虚构内容。
6. 触发升级交付的变更已经生成候选升级包；未完成动态验证时没有标记为正式可发布。
7. 非“仅审计”任务已生成或完善根 `docker-compose.yml`；无法生成时必须作为未完成阻塞报告，不能声明规范建设完成。
