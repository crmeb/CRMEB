# 目录与架构

本文给出可迁移的职责模型。目标项目已有成熟约定时，应映射职责而不是机械改名。

## 四层职责模型

| 层级 | 回答的问题 | 典型内容 | 生命周期 |
| --- | --- | --- | --- |
| 项目事实层 | 项目当前如何组成、运行和部署 | 项目概览、架构、开发、API、数据、部署、运维 | 随代码同步更新 |
| AI 协作层 | AI 应如何理解、修改和验证 | `AGENTS.md`、规则、技能、目录约定、验证要求 | 随工程规范更新 |
| 过程记录层 | 为什么改、如何迁移、验收结果是什么 | 方案、ADR、评审、迁移记录、检查报告 | 完成后归档或删除 |
| 测试验证层 | 如何证明系统仍然正确 | 测试地图、测试数据、执行命令、CI 说明、覆盖边界 | 随测试体系更新 |

同一事实只在一个层级拥有正文。例如：

- “Node 版本要求”归开发运行指南；AI 规则只链接过去。
- “目录禁止放什么”归工程或 AI 规则；根 README 只给入口。
- “某重构尚未实施”归方案；落地后把当前结果更新到正式文档。
- “如何执行集成测试”归测试索引；方案只记录为什么增加它。

## 推荐目录

没有既有约定时，可从以下最小结构开始：

```text
repository/
  README.md                  项目单一入口
  AGENTS.md                  AI 发现入口，保持简短
  backend/                   全部后端代码与后端测试
  frontend/                  全部前端应用与前端共享包
    admin/                   示例：管理端（按真实应用命名）
    web/                     示例：桌面 Web 端
    mobile/                  示例：移动端/H5/跨端应用
  help/docs/
    README.md                正式文档索引
    overview.md              产品定位、角色、能力边界
    architecture.md          系统结构、模块关系、关键链路
    development.md           环境、安装、配置、启动、构建
    testing.md               测试地图、命令、依赖与覆盖边界
    api.md                   API 约定或权威 API 文档入口
    database.md              数据模型、迁移、备份恢复边界
    deployment.md            部署、升级、回滚、健康检查
    operations.md            日志、监控、任务、常见故障
    docker-development.md    Docker 本地开发、调试与数据维护
    upgrade.md               升级包生成、安装、验证与失败恢复
  .crmeb/                    AI 规则、技能与子智能体唯一来源
    AGENTS.md                规则和技能索引
    rules/
    skills/
    agents/
  tests/                     过程记录层与测试验证层同目录，名称由契约 directories.process 声明（缺省 tests/）
    README.md                过程文档导航 + 测试统一入口；正文可链接 help/docs/testing.md
    plans/
    decisions/
    reports/
  docker/                    镜像与服务配置，不存放业务源码
  compose.yaml               本地开发服务编排入口
  upgrades/
    versions/                版本迁移与升级定义真源
    packages/                自动生成的升级包；通常由 .gitignore 排除
```

只创建有真实内容和明确维护者的文件。小型项目可合并 `overview`、`architecture` 和 `development`；无数据库或部署职责的项目不应制造空文档。

## 代码目录统一规范

### 后端 `backend/`

- 所有服务端业务代码、依赖清单、迁移和后端测试统一位于 `backend/`。
- 单体项目直接在 `backend/` 内按框架惯例组织；多服务项目使用 `backend/apps/<服务名>/`，共享库使用 `backend/packages/` 或目标语言的标准 workspace 结构。
- 不在仓库根目录散落 `api/`、`server/`、`service/` 等与 `backend/` 并列的后端业务目录。
- 后端命令必须说明是在仓库根还是 `backend/` 执行；Docker 容器内工作目录也应映射到该边界。

### 前端 `frontend/`

- 所有浏览器端、管理端、H5、移动端、桌面端等前端工程统一位于 `frontend/`。
- 每个可独立安装、构建或发布的客户端使用 `frontend/<应用名>/`，例如 `frontend/admin/`、`frontend/web/`、`frontend/mobile/`。
- 多应用共享组件和 SDK 使用 `frontend/packages/` 或 `frontend/shared/`；其依赖关系由 workspace 配置显式声明。
- 不在根目录散落 `admin/`、`web/`、`h5/`，也不把前端构建产物放进 `backend/` 源码。若部署必须复制静态产物，应由构建或发布脚本完成并记录来源。

### 已有项目迁移

新项目直接遵守上述命名。已有项目目录不一致时，先盘点以下引用再迁移：

- import、autoload、workspace 与构建入口；
- Docker build context、volume 和工作目录；
- CI、部署、Nginx、进程管理与脚本路径；
- 文档、测试、代码生成器和 IDE 配置。

目录迁移应作为独立变更，保留可回滚方案并运行构建、测试和启动验证。用户只要求完善文档时，只记录目标结构和迁移方案，不擅自移动业务代码。

## 入口设计

### 根 README

根 README 是导航页，不是所有内容的复制品。它至少应让读者快速得到：

1. 项目解决什么问题；
2. 主要目录或子项目是什么；
3. 最短可运行路径是什么；
4. 开发、测试、部署、贡献和 AI 规则在哪里；
5. 哪些事项必须先阅读。

### AI 入口

根 `AGENTS.md` 或工具发现文件应保持短小，只负责：

- 指向规则唯一来源；
- 说明更深目录存在作用域更小的规则；
- 告诉 AI 如何选择技能和验证方式；
- 禁止明显高风险行为。

不要在多个工具目录复制整套规则。工具必须使用不同发现路径时，优先使用链接、薄入口或生成校验机制，并明确唯一维护源。

AI 规则正文统一维护在 `.crmeb/`：

- `.crmeb/AGENTS.md`：项目总入口与索引；
- `.crmeb/rules/`：违反即错误的强制规则；
- `.crmeb/skills/`：任务操作流程和专项手册；
- `.crmeb/agents/`：可选的专项角色说明；
- `.crmeb/scopes/`：可选的子项目或目录补充约定。

根 `AGENTS.md`、`CLAUDE.md`、`llms.txt` 等仅作为发现入口并指向 `.crmeb/AGENTS.md`，不复制正文。若目标工具需要专属目录，使用薄入口或软链接，并提供链接完整性检查。

默认生成 Codex/AGENTS、Claude Code、Cursor、GitHub Copilot 和 Gemini CLI 的薄入口，具体路径和验证方式见 [AI 工具适配](ai-tool-adapters.md)。跨平台项目默认使用真实薄文件，只有确认 Git 与开发环境支持时才使用软链接。

### 文档索引

按用户任务组织导航，例如“第一次运行”“理解架构”“开发接口”“写测试”“部署排障”，而不是只按字母或文件名罗列。

## 权威来源矩阵

为易漂移事实定义权威来源：

| 事实 | 推荐权威来源 | 文档写法 |
| --- | --- | --- |
| 语言和框架版本 | manifest、lockfile、运行镜像 | 标注来源，避免凭记忆填写 |
| 启动/构建命令 | package scripts、Makefile、任务配置 | 给出执行目录和前置依赖 |
| 服务端口 | 环境样例、容器、服务配置 | 区分默认值和可覆盖值 |
| API 路由 | 路由定义、OpenAPI 生成物 | 链接权威定义，避免手抄全量接口 |
| 数据表和迁移 | migration/schema | 自动生成或校验数量与关键对象 |
| 模块/插件清单 | 注册器、模块目录、配置 | 用脚本校验，说明启用条件 |
| 测试范围 | 测试配置、目录、CI | 说明已覆盖和未覆盖部分 |
| 部署流程 | 实际部署配置、流水线 | 区分本地示例与生产流程 |
| Docker 本地开发 | `compose.yaml`、Dockerfile、环境样例 | 说明源码挂载、端口、健康检查、数据卷和重建条件 |
| 版本与升级 | 版本文件、发布标签、迁移和升级 manifest | 已发布记录不可回改，生成包与真源可追溯 |

## 生命周期

1. 设计阶段：方案进入过程记录层，明确状态、负责人或核对日期。
2. 实施阶段：代码、测试和正式文档在同一变更中更新。
3. 验收阶段：报告记录已执行验证、结果和未覆盖项。
4. 完成阶段：把已落地事实合并到正式文档；过程文档归档或删除。
5. 维护阶段：CI 或定期检查发现链接、命令和事实漂移。

建议在贡献规范中加入“变更是否需要更新文档”的检查项，但不要承诺不存在的自动化流程。
