# 可复用模板

以下模板是内容骨架，不是必须保留的章节。填写前先用代码和配置核对事实；不适用的章节直接删除。

## 根 README

```markdown
# 项目名称

一句话说明项目面向谁、解决什么问题。

## 项目组成

用短表格说明主要应用/服务、目录和职责。

## 快速开始

### 前置环境

列出版本要求，并注明来源文件。

### 本地运行

1. 安装依赖：命令、执行目录。
2. 创建配置：从哪个示例复制、哪些变量必填。
3. 初始化依赖：数据库/缓存/迁移命令。
4. 启动应用：命令和默认访问地址。
5. 验证成功：健康检查、页面或最小测试。

## 常用命令

开发、构建、测试、lint、类型检查；只列真实存在的命令。

## 文档导航

- 第一次开发：链接
- 理解架构：链接
- API 与数据：链接
- 测试与验证：链接
- 部署与运维：链接
- AI 协作规则：链接

## 安全提示

仅保留对本项目真实且重要的提示。
```

## 正式文档索引

```markdown
# 项目文档

本文档描述当前已实现状态。方案和历史记录位于过程文档目录。

## 按任务查找

| 你要做什么 | 阅读内容 | 适用范围 |
| --- | --- | --- |
| 从零运行项目 | 开发运行指南 | 全体开发者 |
| 理解系统边界 | 项目概览、架构 | 开发与维护者 |
| 开发接口或页面 | API、前端/后端约定 | 对应子项目 |
| 修改数据结构 | 数据库与迁移 | 后端与运维 |
| 编写或运行测试 | 测试索引 | 开发与 CI |
| 部署和排障 | 部署、运维 | 运维与负责人 |
```

## 开发运行指南

```markdown
# 开发运行指南

## 环境要求

列出语言、包管理器、数据库、缓存、容器及版本证据。

## 目录与应用入口

说明各命令应在哪个目录执行。后端统一位于 `backend/`；每个前端应用统一位于 `frontend/<应用名>/`。

## 安装依赖

给出可复制命令、前置条件和成功信号。

## 配置

列出环境变量名、用途、是否必填、默认值来源；不包含真实秘密。

## 初始化与启动

按实际依赖顺序列步骤，区分本地和容器方式。

Docker 本地开发使用独立的 `docker-development.md`，覆盖服务/端口、首次启动、源码挂载、日常命令、依赖重建、数据库持久化和故障排查。

## 构建与测试

列出项目真实脚本，并链接测试索引。

## 常见问题

只收录已复现的问题、症状、原因和验证过的处理方式。
```

## 独立应用说明

为后端及每个 `frontend/<应用名>/` 分别生成应用说明，不能复制同一份模板后只改标题。应用目录 `README.md` 保持短小，提供应用定位、最短运行命令、验证信号和详细文档链接；`help/docs/applications/<应用ID>.md` 记录从当前代码核对出的完整事实。

```markdown
# 应用名称

## 用途、用户与边界
## 技术栈、版本及证据来源
## 目录、入口、路由/页面与关键模块
## 配置、环境变量、端口和依赖服务
## 安装、开发、检查、测试、构建和预览
## API、鉴权、状态与错误处理
## 构建产物、部署/发布目标与平台差异
## 调试、日志、常见故障和已知限制
## 关联架构、数据库、Docker 与测试文档
```

生成或更新前必须检查该应用自己的 manifest、lockfile、构建配置、入口/路由、环境样例、API 客户端、测试和 CI；不得从另一个前端或后端应用推断命令与端口。

## AI 入口

```markdown
# AI 开发入口

处理本仓库任务前：

1. 阅读规则唯一来源：链接。
2. 按目标文件所在目录继续读取更具体的作用域规则。
3. 从技能索引选择与任务匹配的技能。
4. 修改前检查工作区状态，保留已有改动。
5. 完成后执行该模块规定的最小验证，并准确报告未覆盖项。

项目事实以正式文档和可执行配置为准；待实施方案不得视为当前能力。
```

AI 入口保持简洁。编码细则、目录规则、前端/后端约定和专项工作流分别进入规则或技能文件。

规则正文固定维护在 `.crmeb/`。根级及工具专属入口只指向 `.crmeb/AGENTS.md`，不得复制规则全文。

同时生成并校验 `AGENTS.md`、`CLAUDE.md`、`GEMINI.md`、`.cursor/rules/project-standard.mdc`、`.github/copilot-instructions.md` 和 `llms.txt`；入口内容和发现机制见 [AI 工具适配](ai-tool-adapters.md)。

## Docker 本地开发文档

使用 [Docker 本地开发规范](docker-local-development.md) 中的完整要求生成 `help/docs/docker-development.md`。建议结构：

```markdown
# Docker 本地开发

## 适用范围与已验证版本
## 服务、端口、健康检查与数据卷
## 首次启动
## 日常启动、停止与日志
## 本地源码挂载与热更新
## 安装依赖与重建镜像
## 数据库初始化、迁移、备份与恢复
## 在容器内运行测试和调试
## 安全清理与数据保留
## 常见故障
## 与生产环境的差异
```

不要只写 `docker compose up -d`。每个命令都要说明执行目录、前置条件、成功信号和数据影响。

完整项目还应按 [文档覆盖矩阵](documentation-coverage.md) 生成项目概览、配置、前后端、API、数据库、部署、运维、安全、排障、备份恢复和升级回滚文档。只创建标题或保留占位符不算完成；不适用的文档应在索引中说明原因，而不是静默遗漏。

## 升级与发布文档

需要支持存量项目升级时，使用 [自动升级包规范](upgrade-package.md) 生成升级定义、打包命令和验证流程。正式文档建议包含：

```markdown
# 升级与回滚

## 版本策略与唯一版本源
## 支持的来源版本和升级路径
## 升级包目录、manifest 与校验和
## 生成升级计划和升级包
## 升级前预检与备份
## 安装升级包
## 数据库迁移与基础数据处理
## 升级后健康检查
## 失败停止、恢复与回滚边界
## 插件/扩展包与核心升级包边界
## 发布记录和制品留存
```

不得把“覆盖文件并执行 SQL”作为完整升级说明。文档必须包含来源版本限制、备份、校验、失败处理和实际验证范围。

## 文档变更交付摘要

```markdown
已完成项目文档体系的审计与完善：

- 新增/修复：列出入口和职责变化。
- 事实核对：列出版本、命令、路径、路由等证据来源。
- 已运行验证：逐条列命令和结果。
- 未运行验证：列原因和影响范围。
- 待确认：只列必须由项目负责人决策的事项。
```
