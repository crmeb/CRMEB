# 自动升级包规范

本规范用于把已经完成并验证的程序变更自动归档为可追溯、可校验、可安装的增量升级包。它不是完整源码备份，也不替代正式发布流程。

## 触发判定

以下变更通常触发升级包：

- `backend/` 中的业务代码、配置模板、命令或运行资源；
- `frontend/<应用名>/` 中需要发布的代码，包内通常收录构建产物；
- 数据库结构、基础数据、权限、菜单、任务、配置项等迁移；
- 反向代理、进程、容器或部署配置的可交付变化；
- API 契约变化要求后端和前端同步升级。

纯文档、测试源码、CI 配置、开发过程记录通常不触发程序升级包。项目拥有独立插件或扩展体系时，插件自身文件和迁移必须进入插件包，不得混入核心升级包；核心新增扩展契约时才把核心部分放入升级包，并声明所需插件版本。

开始打包前使用 `git diff --name-status`、任务基线提交和构建清单确定本次真实变更。工作区含有其他人的未提交改动时，不得把整个工作区直接归档。

## 统一目录

```text
upgrades/
  versions/
    <target-version>/
      manifest.json           升级定义与约束真源
      CHANGELOG.md            面向使用者的变化和人工步骤
      migrations/             数据结构和基础数据迁移
      hooks/                  preflight/apply/postcheck/rollback（按需）
  packages/
    <project>-<from>-to-<target>.zip
```

`versions/` 中的文本定义和迁移应入库；`packages/` 是可重复生成的发布产物，通常由 `.gitignore` 排除并交给制品仓库保存。目标项目已有成熟升级目录时保留其结构，但必须满足同等职责。

生成的压缩包建议采用以下结构：

```text
manifest.json
CHANGELOG.md
checksums.sha256
payload/
  backend/                    后端源码或编译产物，按技术栈决定
  frontend/<app>/             各前端应用的发布构建产物
  config/                     允许覆盖的非敏感配置模板
migrations/
hooks/
```

不得打包 `.env`、密钥、日志、缓存、runtime、上传文件、数据库备份、IDE 配置、测试数据、宿主机依赖目录或用户生成内容。是否包含 `vendor`、`node_modules`、二进制依赖由项目部署模型决定，并在 manifest 中明确；默认不包含。

## Manifest 必备字段

`manifest.json` 至少记录：

```json
{
  "schema_version": 1,
  "project": "project-id",
  "version": "1.4.0",
  "from_versions": [">=1.3.0 <1.4.0"],
  "created_at": "ISO-8601 UTC time",
  "source_commit": "full git commit id",
  "components": ["backend", "frontend/admin", "database"],
  "requires": {
    "runtime": {},
    "database": {},
    "extensions": []
  },
  "migrations": [],
  "hooks": {},
  "backup": {
    "required": true,
    "scope": []
  },
  "rollback": {
    "supported": false,
    "instructions": "CHANGELOG.md"
  },
  "breaking_changes": [],
  "manual_steps": [],
  "files": []
}
```

字段值必须由版本配置、Git、构建结果和迁移定义生成，不能保留示例值。`from_versions` 应明确允许的来源版本；跨多个版本时必须证明迁移链连续。`files` 记录相对路径、类型、大小和 SHA-256，压缩包根目录另生成 `checksums.sha256`。

## 版本规则

1. 从项目唯一版本源读取当前版本，并与发布标签、manifest、前后端版本字段核对。
2. 优先使用项目已经声明的 SemVer 或版本策略，不擅自发明编号规则。
3. 已发布或已登记为执行成功的版本定义、迁移和 manifest 禁止回改；新增内容必须创建更高版本。
4. 若存在尚未发布的当前开发版本，可在不破坏已验证迁移顺序的前提下合并；否则创建新版本。
5. 无法唯一判断目标版本或升级基线时，先生成升级计划和变更清单，不得冒充最终发布包。
6. 版本提升、Git tag、发布和上传制品是不同动作；生成本地升级包不自动授权推送或发布。

## 数据迁移

- 迁移按稳定顺序执行，每项有唯一 ID，升级器记录执行状态。
- 建表、加字段、加索引和写基础数据应尽可能幂等；重复执行不能造成重复数据或不可控失败。
- UPDATE/DELETE 必须有精确条件，并在需要时记录影响行数上限或预检结果。
- 大表变更采用分阶段兼容方案，避免长事务锁表；先兼容读写，再迁移数据，最后清理旧结构。
- 新安装 schema 与存量升级迁移必须得到相同的最终结构和基础数据。
- 不可逆迁移必须在 manifest 标记、强制备份并提供人工恢复方法；不得伪造 rollback 脚本。
- 迁移涉及插件或扩展数据时遵守其所有权边界，不直接修改不属于核心的私有数据。

## 自动生成流程

目标项目应提供统一命令，命令名可映射到现有构建系统：

```bash
./run.sh upgrade-plan <target-version>
./run.sh upgrade-package <target-version>
./run.sh upgrade-verify <package-path>
```

自动流程必须：

1. 确认基线版本、目标版本、源码提交和工作区范围；
2. 收集任务相关文件，区分核心、插件、文档、测试和发布产物；
3. 检查数据库或基础数据变化是否拥有迁移，并检查迁移链连续性；
4. 执行后端构建或依赖准备，构建所有受影响的前端应用；
5. 只复制发布所需文件，保持相对路径、文件权限和大小写；
6. 生成 manifest、CHANGELOG、文件清单和 SHA-256；
7. 扫描禁止内容和疑似密钥，确认包内没有路径穿越或指向包外的软链接；
8. 生成确定性压缩包，同一提交和配置重复构建应得到相同文件清单；
9. 执行静态校验和隔离升级测试；
10. 输出版本、来源提交、包路径、校验和、覆盖组件和未验证项。

构建脚本不得使用整个仓库复制后再靠黑名单删除的方式出包；应由 manifest 和受影响组件白名单收集文件，降低混入凭据与运行数据的风险。

## 安装器执行顺序

通用安全顺序为：

1. 解析并校验 manifest schema、项目 ID、来源版本和运行环境；
2. 验证包级及逐文件校验和；
3. 检查磁盘空间、目录权限、依赖服务和维护模式能力；
4. 按 manifest 创建代码、配置和数据库备份；
5. 进入维护模式或停止写入流量；
6. 解压到临时目录，拒绝绝对路径、`..` 路径穿越和危险软链接；
7. 原子替换或分阶段部署后端及前端产物；
8. 执行迁移和必要的数据处理；
9. 清理缓存、重载进程并运行 postcheck；
10. 健康检查成功后退出维护模式并写入升级日志；
11. 失败时停止后续步骤，按声明恢复文件和数据，保留可排障日志。

不同技术栈可调整文件与迁移先后，但必须避免新代码与旧数据库长期不兼容。使用滚动发布时，迁移应同时兼容升级中的新旧实例。

## 验证矩阵

| 验证 | 最低要求 |
| --- | --- |
| 静态包检查 | manifest schema、允许来源版本、文件清单、禁止内容、路径安全、SHA-256 全部通过 |
| 构建验证 | 所有受影响的后端和前端产物从干净环境生成 |
| 新安装一致性 | 新安装与执行全部迁移后的 schema/基础数据一致 |
| 幂等性 | 可重复的迁移在临时库连续执行两次结果稳定；一次性迁移能被升级日志可靠跳过 |
| 单级升级 | 最近稳定版到目标版成功，健康检查和核心 smoke 通过 |
| 跨级升级 | 声明支持的最低版本沿完整迁移链升级成功 |
| 失败恢复 | 至少验证一个迁移或 postcheck 失败场景，确认不会标记为成功且备份可用 |
| 重启验证 | 升级后重启应用、worker、scheduler 等进程仍正常 |

若无法运行数据库、构建或完整升级环境，包只能标记为“候选/未完成动态验证”，不能宣称可发布。

## CI 与交付门禁

- 合并前校验版本单调递增、迁移链连续、manifest 合法、禁止文件和校验和。
- 发布流水线从干净提交重新构建升级包，不信任开发机生成的未知产物。
- 制品仓库保存压缩包、SHA-256、来源提交、构建日志和验证结果。
- 发布说明必须报告目标版本、允许来源版本、包路径或制品地址、SHA-256、迁移概要、备份要求、人工步骤与未验证项。
- 未通过隔离升级测试、含未解决高风险迁移或无法确定来源版本时阻止正式发布。
