# 后端通用规范

## 架构边界

- 依赖方向必须单向且可描述，领域层不依赖 Web、数据库驱动或具体第三方 SDK。
- Controller/Handler 负责协议适配、鉴权入口和参数转换，不承载核心业务。
- Service/UseCase 编排业务和事务；Repository/DAO 隔离持久化；外部服务通过 Adapter/Gateway 隔离。
- 跨模块调用通过公开契约、事件或接口，不引用对方内部实现。
- 框架确有不同最佳实践时，在 `.crmeb/rules/backend.md` 写清实际分层和例外。

## 数据与事务

- 事务边界位于业务用例层，事务内避免不受控网络调用和长耗时处理。
- 写操作明确并发、幂等和重试语义；支付、库存、回调、任务尤其如此。
- 查询必须分页，避免 N+1、无边界全表加载和 `SELECT *` 类不稳定契约。
- 缓存必须定义 key、TTL、失效责任和一致性策略，不把缓存当权威数据源。

## 输入、错误和日志

- 所有外部输入在边界校验、归一化和限流；内部方法仍维护业务不变量。
- 业务错误、校验错误、权限错误、依赖故障和未知异常分层映射。
- 不吞异常、不空 catch、不把堆栈或敏感数据返回客户端。
- 结构化日志包含请求/任务关联 ID、模块、动作和结果；密码、令牌、Cookie、身份证件等必须脱敏。

## 异步任务

- 队列消息和事件 payload 版本化，消费者可幂等处理和安全重试。
- 定时任务和 worker 明确超时、重试、退避、死信和人工补偿。
- 进程入口纳入标准 status/logs/healthcheck，升级后验证重启与积压情况。

## 验证

- 领域规则优先单元测试；数据库和外部适配使用集成测试。
- 权限、并发、幂等、事务回滚、重试和失败补偿必须覆盖高风险路径。
- 使用该语言 Profile 中项目真实存在的 lint、类型、测试和构建工具。

## 后端应用说明文档

- 后端目录必须维护就近 `README.md`，并链接到 `help/docs/applications/<后端ID>.md` 的详细说明；多后端应用或服务要分别建档。
- 根据当前 manifest/lockfile、框架入口、路由、配置样例、迁移、worker/scheduler、测试和 CI 核对技术栈、版本、分层、命令、端口、依赖服务和健康信号。
- 修改运行时、扩展、启动入口、路由/API、配置、数据库、异步进程、测试或部署方式时，同一变更检查并更新对应说明。
- 旧说明与代码不一致时，以代码、配置和实际执行结果为准，并明确尚未动态验证的内容。
