# 文档与事实治理

## 1. 先建立证据账本

对每项关键事实记录四个字段：

| 事实 | 证据 | 验证方式 | 状态 |
| --- | --- | --- | --- |
| 运行时版本 | manifest、lockfile、容器镜像 | 读取约束并与实际环境比较 | 已核对 / 冲突 / 未验证 |
| 启动命令 | scripts、Makefile、compose | 在正确目录执行或静态解析 | 已运行 / 仅静态 |
| API 前缀 | 路由注册文件 | 搜索注册链路，必要时列路由 | 已核对 / 待运行 |
| 数据结构 | migrations、schema | 解析迁移或连接测试库 | 已核对 / 环境受限 |

先收集证据，再决定写什么。遇到冲突时报告冲突并以可执行配置为优先，不应选择看起来更合理的旧描述。

## 2. 项目发现顺序

### 仓库与规则

- 根目录、Git 状态、远程托管平台；
- 所有适用的 `AGENTS.md`、贡献指南和目录规则；
- workspace/monorepo 配置和各子项目边界；
- 当前未提交修改，避免覆盖或误归因。

### 技术栈与依赖

- manifest、lockfile、运行镜像和版本文件；
- 后端、前端、移动端、插件、任务进程等入口；
- 包管理器、构建工具、代码生成、数据库和缓存；
- 生产依赖与仅开发依赖的区别。

### 可执行工作流

- 安装、初始化、启动、停止、构建、测试、lint、类型检查；
- 环境变量样例、配置覆盖顺序、默认端口；
- 数据库创建、迁移、种子、升级、备份和回滚；
- 容器、CI、发布、健康检查和日志位置。

项目存在 Dockerfile 或 Compose 时，还要确认它是生产构建、本地开发还是两者兼有，并检查源码是否挂载、依赖目录如何隔离、服务是否有健康检查。详细检查使用 [Docker 本地开发规范](docker-local-development.md)。

### 系统结构

- 请求入口、路由、控制器/服务/数据访问层；
- 前端路由、状态管理、API 客户端和构建产物；
- 异步任务、定时器、WebSocket、缓存、文件存储；
- 插件或模块的发现、安装、启停、卸载和权限边界。

### 验证资产

- 单元、集成、端到端、契约、冒烟测试；
- fixture、测试数据和依赖服务；
- CI 实际执行的检查；
- 本地无法覆盖的动态路径。

### 版本与升级资产

- 唯一版本源、发布标签、历史版本和允许升级范围；
- 数据库迁移、基础数据迁移、升级日志和失败恢复机制；
- 后端发布物、各前端应用构建产物及配置覆盖边界；
- 现有升级器、manifest、校验和、备份与回滚能力；
- 核心升级包与插件/扩展包的所有权边界。

需要生成或修复升级交付时使用 [自动升级包规范](upgrade-package.md)，不得仅依据工作区全部改动直接压缩。

## 3. 差距评估

按以下维度给出“完整 / 部分 / 缺失 / 冲突”，每条结论必须附证据：

1. 发现性：根入口是否能到达所有关键文档；
2. 正确性：版本、路径、命令、端口、路由是否与代码一致；
3. 可运行性：新环境是否有从零到运行的闭环；
4. 可开发性：架构、目录、规则和扩展方式是否明确；
5. 可验证性：测试层级、命令、成功信号和限制是否明确；
6. 可运维性：部署、升级、回滚、日志、监控是否覆盖；
7. AI 友好性：规则是否可发现、范围是否清楚、验证是否可执行；
8. 可维护性：是否存在重复真相源、失效链接和自动校验缺口。
9. 目录一致性：AI 规则、后端与前端是否分别归入 `.crmeb/`、`backend/`、`frontend/`，不一致时是否有安全迁移方案。
10. 升级能力：旧版本能否通过连续迁移、安全文件替换和验证步骤升级，失败时是否可停止并恢复。
11. 文档覆盖：按 [项目文档覆盖矩阵](documentation-coverage.md) 检查通用文档与数据库、UniApp、异步进程、Docker、升级等条件文档，防止只补 README 和启动说明。

## 4. 实施策略

### 先修 P0

- 错误或危险命令；
- 泄露的凭据或真实环境数据；
- 根入口和实际项目完全脱节；
- 多份文档对同一事实给出冲突结论；
- 把待实施方案写成当前能力。

### 再补最短闭环

以新接手者路径实施：

1. 从根 README 识别项目；
2. 安装正确版本的运行环境和依赖；
3. 从样例建立本地配置；
4. 启动最小依赖和应用；
5. 确认健康状态或首个可见页面；
6. 运行最小测试或静态检查；
7. 找到架构、接口、数据和贡献规则。

命令块附近要写明执行目录、前置服务、预期结果。若某一步只适用于特定平台或版本，应紧邻命令说明。

### 最后治理漂移

优先校验最容易变化且能低成本提取的事实：

- Markdown 内部链接与路径；
- 运行时版本和包管理器；
- 公开脚本名称；
- 模块、插件、数据库迁移或路由的关键清单；
- 根入口是否链接到规则和测试索引。

校验脚本应失败得清楚：指出文档值、实际值和证据位置。不要只检查“文件存在”，也不要为不可稳定解析的内容制造脆弱正则。

## 5. 验证分级

| 级别 | 含义 | 可声明的结论 |
| --- | --- | --- |
| L0 文本检查 | 格式、链接、路径、拼写 | 文档结构与引用有效 |
| L1 静态事实检查 | 从配置/代码解析版本、脚本、路由等 | 文档与当前源码一致 |
| L2 构建/测试 | 安装、lint、类型检查、单测、构建 | 对应检查在当前环境通过 |
| L3 运行验证 | 启动服务、健康检查、集成/冒烟测试 | 指定运行链路已实际验证 |
| L4 生命周期验证 | 安装、升级、回滚、插件启停/卸载 | 指定生命周期场景已验证 |

报告必须使用实际达到的级别。L0/L1 不能写成“项目可正常运行”，单元测试通过也不能替代部署或升级验证。

## 6. 环境与安全边界

- 不读取或输出真实密钥、令牌、Cookie、个人数据；环境示例只保留占位值。
- 不因文档检查擅自连接生产库、运行生产迁移、删除数据或发布版本。
- 不默认容器存在或能启动；先检查运行时、镜像和服务状态。
- 不把本机偶然路径写成所有开发者的固定要求，除非项目本身规定如此。
- 添加 CI 前先确认托管平台和现有流水线；非 GitHub 项目不要擅自添加 GitHub Actions。
- 依赖不可用时，完成安全的静态验证并明确动态覆盖缺口。

## 7. 审计输出格式

仅审计时，推荐用表格输出：

| 优先级 | 问题 | 证据 | 影响 | 建议 |
| --- | --- | --- | --- | --- |
| P0/P1/P2 | 明确且可复现的问题 | 文件、配置或命令结果 | 对运行/开发/AI 的影响 | 最小可实施动作 |

结尾给出建议实施顺序和验证计划。没有证据的推测单独标注为“待确认”。
