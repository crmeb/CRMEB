# 升级程序包规范（二开改动归档）

## 当前版本阶段例外

当前仓库处于 CRMEB-BZ v8 首个正式版本发布前的开发阶段。本阶段直接维护源码和全新安装数据，**暂不创建版本增量脚本、升级配置条目、升级包目录或升级包压缩文件**。首个正式版本发布后，删除本节并恢复本规范其余章节的升级包要求。

本仓库是开源项目，二开者会在旧版本站点上增量升级。因此首个正式版本发布后，**任何改变程序文件或数据库的二开改动，完成时必须自动归档为一个升级程序包**，使老站点可以不推倒重来地升级到新版本。

## 1. 触发条件

首个正式版本发布后，二开任务满足以下任一条，即必须归档升级包（在提交/交付前完成，见第 5 节流程）：

1. 后端代码改动：`backend/app/`、`backend/crmeb/`、`backend/driver/`、`backend/config/`；
2. 数据库结构或系统字典数据变更：建表/改表/加索引、菜单（`system_menus`）、配置项、通知模板等基础数据变化；
3. 前端代码改动：`frontend/admin/`、`frontend/uni-app/`（升级包收录其**构建产物**）；
4. `backend/public/` 下模板、静态资源、安装 SQL 的改动。

**不触发**：纯文档、测试、CI 配置、`tests/` 过程产物（`plans/`、`reports/`）的改动。

## 2. 升级包 vs 插件包边界（铁律）

| 改动位置 | 归档去向 |
| --- | --- |
| `backend/modules/**` 中带有效 `plugin.json` 的模块（含其 Installer、路由、前端扩展产物） | **只进插件包**：按[插件开发规范](插件开发规范.md)第七节打包与归档，安装/升级走后台插件上传接口与 Installer |
| 核心路径（`app/`、`crmeb/`、`driver/`、`config/`、`frontend/`、非插件 `public/` 资源） | **进升级包** |
| 一次改动同时含两者（如插件需要核心新增契约钩子） | 拆开：核心部分入升级包，插件部分入插件包；升级包 `manifest.json` 的 `plugins_required` 声明依赖的插件 key 与最低版本 |

判定标准：文件路径是否属于某个含 `plugin.json` 的模块目录。**升级包内出现插件文件即违规**——插件独立分发是插件可卸载、可单独升级的前提。

## 3. 版本增量脚本（首发后包的骨架，必做）

- 位置：`backend/upgrade/versions/` 目录下，文件名按版本号 `vX.Y.Z.php`；脚本返回数组，键为 `version` / `code` / `description` / `update_sql` / `update_file`。
- 版本号：`code = major*100 + minor*10 + patch`（如 v8.0.1 → 801），与文件名严格一致，**只增不减**。
- `update_sql` 条目：`type` 语义（1 建表、2 删表、3 加字段、4 改字段、5 删字段、6 加数据、7 改数据、8 删数据、-1 直接执行）；SQL 中表名一律用 `` `@table` `` 占位符，同时在 `table` 字段给出去前缀表名；**禁止硬编码 `eb_` 前缀**。
- **SQL 必须幂等**：加字段/索引前先判存在；插数据用 `REPLACE INTO` 或先查后插；UPDATE/DELETE 必须带明确 WHERE。幂等的原因：执行方按 `upgrade_log` 跳过已执行版本，但同一脚本在别的站点可能因手工二开已部分落库。
- 已执行过（已在 `upgrade_log` 登记）的版本脚本**禁止回改后指望老站点重跑**：新增内容一律开新版本号。
- `update_file`：本版本改动的后端文件清单（相对 `backend/` 根，每文件一项），供手工核对与增量部署。
- 注册：`backend/config/upgrade.php` 的 `versions` 数组按 `code` 升序追加，不动既有条目。
- 表结构变更**双写**：升级 SQL（存量升级）+ 同步 `backend/public/install/crmeb_table.sql`（全新安装），两份保持一致（见[数据库规范](数据库规范.md)）。

## 4. 升级程序包结构与存放

存放位置：`backend/upgrade/packages/{version}/`，同目录压缩出 `{version}.zip`。

```
backend/upgrade/packages/v8.0.1/
├── manifest.json                  # 包清单（见 4.2）
├── config/                        # backend/config 全量目录 —— 线上升级必检项
├── upgrade/versions/v8.0.1.php    # 本版本增量脚本 —— 线上升级必检项
├── backend/                       # 改动后端文件的增量副本，相对 backend/ 保留目录结构
├── frontend/admin/                # admin 构建产物（有前端改动时）
├── frontend/h5/                   # uni-app H5 构建产物（有移动端 H5 改动时）
└── sql/                           # 人工辅助 SQL（与版本脚本 update_sql 内容一致，可选）
```

- **`config/` 与 `upgrade/versions/` 必检**：在线升级服务（`UpgradeServices`）下载包后先校验这两项存在并覆盖到项目，缺一则升级直接失败。
- 4.1 包内 `frontend/` 收录**构建产物**而非源码：`admin/` 子目录放管理端 build 输出（部署到站点 `/admin` 路径），`h5/` 子目录放移动端 H5 产物。小程序/APP 端无法靠升级包替换，必须在 manifest 的 `frontend_notice` 注明"小程序端需重新构建并上传审核"。
- 4.2 `manifest.json` 必备字段：

```json
{
  "version": "CRMEB-BZ v8.0.1",
  "code": 801,
  "base_min_version": "CRMEB-BZ v8.0.0",
  "created_at": "2026-09-17",
  "changes": ["feat(goods): xxx", "fix(order): yyy"],
  "backend_files": ["app/services/goods/GoodsService.php"],
  "database": ["goods", "order_center"],
  "frontend": ["admin", "h5"],
  "frontend_notice": "admin 产物覆盖部署到 /admin；小程序需重新构建上传",
  "plugins_required": {"cardkey": ">=1.0.1"},
  "rollback": "升级前自动备份；失败恢复 backup/ 中数据库与项目备份"
}
```

- **版本字符串功能格式红线**：`.version` 文件、`config/upgrade.php`、版本脚本与 manifest 中参与机器解析的版本值必须保持 `CRMEB-BZ vX.Y.Z` 格式——升级服务用 `str_replace('CRMEB-BZ v', '', ...)` 解析版本号。文档中的项目名统一为"CRMEB v8"，但**不得顺手改掉这些功能字段**，改了直接破坏版本比较与升级链路。
- 入库边界：目录结构、版本脚本、`manifest.json`、`backend/` 增量文本入库；`*.zip` 与 `frontend/` 构建产物为二进制大文件，由 `.gitignore` 排除（发布物在出包时现生成）。

## 5. 自动执行流程（交付前，AI 必做）

首个正式版本发布后，完成第 1 节任一触发条件的改动，在提交前自动执行：

1. `git diff --name-only` 收集本任务改动文件清单；
2. 按第 2 节分界：插件文件 → 转插件打包流程；核心文件 → 进入升级包；
3. 确定版本号：本轮尚未封包的在途改动**追加进当前版本脚本**（SQL 按时序追加、`update_file` 去重合并），否则 patch +1 开新版本；
4. 写/更新版本脚本（SQL 增量 + update_file），并注册 `config/upgrade.php`；表结构改动同步 install SQL；
5. 按第 4 节结构收集文件：`config/`、`upgrade/versions/` 必带；后端改动文件按相对路径复制进 `backend/`；有前端改动则先构建对应端（admin `npm run build`、H5 `npm run build:h5`），产物复制进 `frontend/`；
6. 生成/更新 `manifest.json`，压缩 `{version}.zip`；
7. 验证：`php -l` 版本脚本；对临时库连跑两遍版本 SQL 确认幂等；`php think arch:check`、`php think docs:check` error 清零；
8. 在交付说明中报告包路径与版本号，作为任务完成判据之一。

## 6. 违规判定

| 行为 | 结论 |
| --- | --- |
| 升级包内混入 `modules/**` 插件文件 | ❌ 违规，插件必须走插件包 |
| 只改代码不落版本脚本，或回改已执行版本脚本期望老站点重跑 | ❌ 违规，老站点将无法增量升级 |
| 升级 SQL 硬编码 `eb_`、缺 WHERE、不可重复执行 | ❌ 违规 |
| 把 `.version` / 升级配置中版本值的 `CRMEB-BZ v` 功能格式改成其他写法 | ❌ 违规，破坏升级链路 |
| 包内缺 `config/` 或 `upgrade/versions/` | ❌ 线上升级校验必失败 |
| 打包 `.env`、`runtime/`、`backup/`、`vendor/`、`uploads/`、密钥或数据库备份 | ❌ 违规（对齐安全红线与提交规范） |
| 改了前端只出后端增量，manifest 又未声明前端变更 | ❌ 违规 |
