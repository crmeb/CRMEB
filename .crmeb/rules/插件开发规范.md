# 插件开发规范（二开强制边界）

> 本文件是插件、驱动与 `backend/modules/` 业务模块二开的**法律条款**：违反任意一条即视为缺陷，必须返工。
> "怎么做"（清单字段、生命周期流程、示例）见技能 [crmeb-plugin-dev](../skills/crmeb-plugin-dev/SKILL.md)；依赖铁律、扩展点总览见 [架构规范.md](架构规范.md)；共享表协议细则见 [架构规范详解.md](架构规范详解.md)「插件间共享表准入协议」。

## 一、总原则（强约束）

1. **零侵入**：插件实现靠扩展点、事件与注册中心，**不靠修改核心**。二开完成的判定标准是：`backend/app/`、`backend/crmeb/`、`backend/driver/` 公共部分、核心前端源码与核心安装 SQL **零 diff**。
2. **可还原**：插件必须可安装、可卸载、可重装。卸载后系统必须回到安装前状态——自有表删除、菜单/配置/协议/DIY 页面链接清理、注册中心与共享表登记释放、自有缓存清理，核心数据不得残留脏数据。
3. **自包含**：插件的一切资源（代码、表、菜单、配置、路由、事件监听、前端资源、定时任务）全部归属插件目录与 Installer 生命周期管理，不向核心目录与核心数据扩散。

## 二、代码边界（强约束）

4. **插件代码只能落自有目录**：业务模块 `backend/modules/{category}/{name}/`、第三方驱动 `backend/driver/{category}/{name}/`；清单 `plugin.json` 的 `path` 必须与实际目录一致。除此之外的任何位置不得新增插件文件。
5. **禁止修改框架代码**，包括但不限于：

   | 禁改区域 | 说明 |
   | --- | --- |
   | `backend/app/` | 统一管理中台：控制器、Service、多应用入口 `adminapi`/`api`/`outapi`、核心路由、`app/event.php`、`AppService.php` |
   | `backend/crmeb/` | 核心底层：services、module、interfaces、注册中心等 |
   | `backend/driver/` 公共部分 | 驱动基类与发现服务；驱动插件只能新增 `driver/{category}/{name}/` 自有目录 |
   | `frontend/admin/src/`（插件源码区除外） | 管理端核心源码禁改：核心页面、公共组件、路由、`src/api`、菜单渲染逻辑；插件页面源码只能落宿主预留的 `src/pages/plugin/<key>/`（见第五节） |
   | `frontend/uni-app/` 核心源码 | 移动端核心页面、组件、`api` 封装、路由与分包配置 |
   | `backend/public/install/` | 核心安装 SQL（`crmeb_table.sql`、`crmeb_data.sql`）禁止为插件而改；`crmeb.sql.bak` 任何情况禁改 |
   | 根 `composer.json`、`backend/config/`、`.env` | 禁止为插件追加 autoload 映射、全局配置项、环境变量 |

6. **禁止一切绕过式 hack**：不得通过类重载/映射覆盖核心类、composer patch、`eval`、反射修改核心类私有属性、替换容器绑定、运行时改写已加载类等方式变更框架行为。核心行为只能通过既有扩展点定制。
7. **依赖方向必须遵守三层铁律**（见 [架构规范.md](架构规范.md)）：插件可调用 `crmeb/`、`app/`；`app/`、`crmeb/`、`driver/` 绝不可反向引用 `modules/`；同级插件互不引用，跨插件通信走核心契约或字符串事件。
8. **监听器只注册在模块自己的 `event.php`**：禁止为挂载插件监听器而修改 `backend/app/event.php`；模块 `App.php` 的 `boot()` 负责加载模块事件。
9. **禁止硬编码模块映射**：绝不能向 `app/AppService.php` 或任何核心类追加模块名/Handler 的静态映射；模块 `App::register()` 与注册中心才是扩展机制。

## 三、数据库边界（强约束）

10. **系统表定义**：`backend/public/install/crmeb_table.sql` 中的全部 `eb_` 前缀核心表（如 `eb_user`、`eb_store_product`、`eb_order_center`、`eb_system_config`、`eb_system_menu`），以及 `eb_shared_table_registry` 等框架设施表。共享业务表（`SHARED_TABLE_CATALOG` 目录内）另按第 13 条协议处理。
11. **禁止对系统表做任何 DDL**：`ALTER TABLE`、`CREATE INDEX`、`DROP`、`RENAME`、改字符集等一律禁止——无论写在插件 `runMigrate()`、升级脚本还是运行时代码里。
12. **系统表"读放行、写走契约"**：
    - **读**：允许通过自有 DAO/Model 只读查询系统表。
    - **写**：只能调用对应核心 Service 的公开方法（如用户、商品、订单变更走相应 Service），禁止裸 SQL / `Db::execute` / 直接 Model `save/insert/update/delete` 绕过业务逻辑直写系统表。
13. **共享表必须走准入协议**：可共享表必须登记在 `BaseModuleInstaller::SHARED_TABLE_CATALOG`，使用方覆写 `sharedTables()` 声明；卸载删共享表必须调用 `dropSharedTableIfUnclaimed()` 仲裁；`cleanTable()` 清理必须携带归属条件。细则与设施见 [架构规范详解.md](架构规范详解.md)「插件间共享表准入协议」，**禁止裸 `DROP TABLE` 目录内共享表**。
14. **插件自有数据只落自有表**：自有表在 `runMigrate()` 创建、`rollbackMigrate()` 删除，表名 `eb_{插件标识}_*`；建表遵守 [数据库规范.md](数据库规范.md)。卸载禁止遗留自有表与脏数据。
15. **菜单、配置、协议、DIY 页面链接必须走 Installer 标准设施**：菜单用 `getMenuConfig()`、种子数据用 `seed()`、清理用 `cleanData()`、DIY 链接用 `ensurePageLinkCategory()`/`seedPageLinks()`；**禁止直接 INSERT/UPDATE/DELETE `eb_system_menu`、`eb_system_config` 等系统表**。驱动设置归属驱动清单与驱动配置存储，禁止写 `system_config`。
16. **插件自有数据不预置核心安装 SQL**：核心安装 SQL 只保留与模块无关的系统级数据（见 [架构规范.md](架构规范.md)「数据库变更规范（强约束）」）。
17. **`cleanData()` 清理范围只覆盖本插件拥有的资源**：禁止无条件范围的 `DELETE`/`UPDATE`/清理查询；清理共享表必须带归属条件（第 13 条）。

## 四、扩展方式（强约束）

18. **只能通过既有扩展点扩展**：产品类型、交易模式、用户渠道、营销玩法四大扩展点（`modules/{category}/{name}/`），支付等基础设施走 `driver/`。Handler 在模块 `App::register()` 注册，禁止在核心注册中心文件中追加注册。
19. **事件用字符串 key**，监听器注册在模块 `event.php`（见 [事件规范.md](事件规范.md)）；监听器扩展共享载荷时使用既有引用结构与命名空间 key，禁止在 `app/` Service 中摊平模块专属字段。
20. **中台独有字段走扩展事件**：商品/订单中台不感知扩展层字段，扩展信息由 `OrderCenterDetailExtend`、`ProductDetailExtend` 等事件注入；禁止为塞入扩展字段而修改中台层代码（见 [架构规范.md](架构规范.md) 高频违规第 5 条）。
21. **前端扩展走插件自有资源**：管理端用 admin UMD 资源与菜单挂载（强制要求见第五节）；移动端独立页面用 `seedPageLinks()` 注册进 DIY 链接选择器，DIY 组件在清单 `diy.components` 声明；新增能力优先向既有前端契约（`display_sections`、`page_config`）添加数据，**不修改核心前端**。

## 五、后台前端扩展（Admin UMD）（强约束）

22. **源码与产物归属**：插件管理端页面源码只能放在 `frontend/admin/src/pages/plugin/<key>/`（宿主预留的插件源码区，必须同时包含 `ext.json` 与 `index.umd.js` 供构建扫描器识别），通过 `npm run build:ext -- --ext <key>` 构建产物 `dist/static/extensions/<key>/app.umd.js|.css`；**禁止为挂载插件页面而修改宿主路由、菜单、布局或任何核心组件**。
23. **可分发资源部署**：随插件分发的构建产物保存在模块自有前端资源目录的 `dist` 子目录，由 Installer 在安装/启用时复制到 `backend/public/admin/static/extensions/<key>/`，禁用/卸载时只删除当前 key 对应的扩展目录；部署必须幂等，**禁止删除其他插件的扩展目录或核心静态资源**。
24. **五处 key 一致**：`plugin.json`/Installer key、`ext.json` key、全局变量名 `window.__ext_<key>`、输出目录 `<key>`、PageContainer `typeKey` 必须完全一致，不一致即安装缺陷。
25. **复用宿主运行时**：扩展必须以 external 方式复用宿主 Vue 3 与 Element Plus（`window.Vue` / `window.ElementPlus`），**禁止打包第二份不兼容的 Vue 运行时**；禁止替换、覆盖或猴子补丁宿主全局组件、指令与原型方法。
26. **样式隔离**：样式必须使用 scoped 或统一限制在扩展专属根 class 下，禁止污染宿主全局样式；主题色只用 `--prev-*` 设计令牌（管理端红线见 [前端规范.md](前端规范.md)，对插件页面同样适用）。
27. **菜单与权限**：插件菜单由 Installer `getMenuConfig()` 注册，菜单路径必须解析到已注册的宿主路由及正确 `section`/`action`，`activeMenu` 与可见列表菜单一致；插件后端接口必须登记权限规则，页面按钮按管理端红线带 `v-auth`——**前端隐藏菜单/按钮不等于安全**（同步清单见 [前端规范.md](前端规范.md) 第三节）。
28. **禁止空页面与现场构建**：必需源码或产物缺失时安装/启用应明确报错，不得留下指向空页面的可见菜单；资源必须在打包前构建完成，**禁止在生产安装请求中现场构建**；禁用/卸载先移除或隐藏菜单，再删除资源。

## 六、生命周期与交付（强约束）

29. **清单与身份一致**：`plugin.json` 必须通过 `PluginManifest::fromFile()` 校验；`key`、Installer、事件、菜单权限、前端扩展 key 全链路一致。
30. **生命周期幂等**：安装、`seed()`、菜单插入、启用、禁用、卸载、重装必须幂等；覆写 `onEnable()`/`onDisable()` 必须调用 `parent::`。
31. **禁止伪造状态**：不得手工修改插件安装日志、缓存或数据库登记来模拟安装/启用成功；只能调用公开生命周期 Service 或管理 API。
32. **缓存隔离**：插件自有缓存使用 `PluginCacheService`（自动隔离 key 与 tag）；禁止调用 `CacheService::clear()/clearAll()` 清空共享缓存池。
33. **打包边界**：插件包只能包含唯一有效 `plugin.json` 的插件根目录；禁止打包本地密钥、运行时数据、无关仓库文件。

## 七、插件包与升级包（交付强约束）

> 本节与 [升级包规范.md](升级包规范.md) 对称：核心文件改动走升级程序包，插件改动走插件包，互不混装（分界见升级包规范第 2 节）。升级由后台插件上传接口承接（`app/adminapi/controller/plugin/PluginController.php`，迁移脚本执行在 `app/services/system/module/ModuleInstaller::runUpgradeMigrations()`），以下约束均由服务端校验逻辑反推——违反即上传被拒或升级失败，必然在交付环节暴露。

34. **插件包结构**：zip 根目录即插件根目录（第 33 条），含有效 `plugin.json`（必填 `key`/`name`/`type`/`version`/`path`，`version` 用 semver）；`path` 必须与实际安装目标一致。type→目标目录映射固定：`product`/`product_type`→`modules/product/`、`activity`/`mode`→`modules/trade/`、`user`/`channel`/`marketing`→同名子目录、`driver`→`driver/{category}/{name}`（类别限 pay/sms/upload/express/logistics/invoice/email/bot/copyproduct/printer）、其余→`modules/`。
35. **zip 安全约束**：包内条目数 1～2000；禁止目录穿越、绝对路径、符号链接、解压炸弹——服务端强制校验，打包阶段违规即被拒。
36. **版本双源一致**：安装时写入 `eb_module_install_log` 的版本来自 Installer 覆写的 `getVersion()`，升级时来自 `plugin.json` 的 `version`，两者不一致会让后续升级误判当前版本。发布新版本必须**同步递增**这两处，且新版本严格大于当前版本（服务端对旧目录清单与安装日志双重比较）。
37. **升级 = 完整目录替换，禁出 diff 包**：向已存在的插件目录上传包即按升级处理，要求 `key`/`type`/`path` 与已装插件同一版本线；旧目录整体备份到 `modules/backup/.plugin_backup/` 并在失败时回滚。因此插件升级包必须携带**完整的新版插件目录**，不得只打包改动文件。
38. **升级迁移脚本**：涉及已安装站点的数据/结构变更，必须在插件根目录的 `upgrades/` 子目录归档迁移脚本，文件名格式「{起始版本}_to_{目标版本}.php」（如 `1.0.0_to_1.1.0.php`），文件返回一个可调用对象。服务端从当前安装版本沿链逐级执行到目标版本：跨多级版本必须提供完整脚本链；包内无任何脚本视为纯代码升级；**有脚本但断链必然升级失败**。脚本只允许操作插件自有表（第 11～14 条对升级脚本同样生效），必须幂等。
39. **升级不重跑生命周期**：插件已安装，升级不会再次执行 `install()` 及启用时的资源部署。新版本若新增菜单、种子数据、共享表登记、DIY 链接，须在升级脚本内做等效操作（复用 Installer 标准设施语义）；若更新了随插件分发的模块自有前端产物（第 23 条所述部署资源），交付说明必须注明"升级后将插件禁用再启用"以触发第 23 条幂等部署，并验证扩展资源生效后才可宣告升级完成。
40. **交付前自动归档插件包**（与升级包规范第 5 节对称）：任务改动插件自有目录（含 `plugin.json` 的 `modules/**` 模块、`driver/{category}/{name}` 驱动）时，提交前自动执行：① 按升级包规范第 2 节确认改动不入核心升级包；② 双源递增版本号（第 36 条）；③ 有数据/结构变更则补 `upgrades/` 迁移脚本（第 38 条）；④ 配套前端扩展先完成产物构建（第 28 条）；⑤ 压缩插件根目录，输出到 tests 过程产物区的 plugin-packages 子目录、文件名含 key 与版本号（该目录已在 .gitignore 排除：zip 为发布产物不入库，真源是插件目录本身，出包时现生成）；⑥ 临时库端到端验证：首发跑安装路径，非首发跑"装旧版 → 上传升级包"路径；⑦ 在交付说明中报告插件包路径、key 与覆盖的版本区间。

## 八、违规判定（验收红线）

交付前逐项自查，任一命中即返工：

| # | 检查项 | 判定 |
| --- | --- | --- |
| 1 | `git diff --name-only` 出现 `backend/app/`、`backend/crmeb/`、`frontend/admin/src/`（插件自有区 `src/pages/plugin/<key>/` 除外）、`frontend/uni-app/` 核心目录、核心安装 SQL、根 `composer.json`/`config/`/`.env`（且本任务非核心开发任务） | ❌ 违规 |
| 2 | 插件目录内出现对系统表的 DDL 或无条件 DML（UPDATE/DELETE/TRUNCATE/DROP） | ❌ 违规 |
| 3 | `app/`、`crmeb/`、`driver/` 出现 `use modules\...` 或对插件类的调用 | ❌ 违规 |
| 4 | 事件调用使用类常量、监听器写进核心 `app/event.php` | ❌ 违规 |
| 5 | 共享表裸 `DROP`、`cleanData()` 出现无条件的删除/更新 | ❌ 违规 |
| 6 | 卸载后存在残留：自有表未删、菜单/配置/协议/DIY 链接未清、共享表登记未释放、admin 扩展资源目录未删或残留空菜单 | ❌ 违规 |
| 7 | admin 扩展五处 key 不一致、打包了私有 Vue 运行时、样式未隔离、生产安装现场构建资源、插件接口未登记权限规则 | ❌ 违规 |
| 8 | 破坏性生命周期操作未在隔离数据库验证、订单相关插件未覆盖完整订单流程 | ❌ 违规 |
| 9 | 发布新版本未同步递增 `plugin.json` 与 Installer `getVersion()` 两处版本，或版本未严格增大 | ❌ 违规 |
| 10 | 有数据/结构变更但未提供（或断链）`upgrades/` 迁移脚本；升级脚本对系统表 DDL/DML；升级包只含 diff 文件而非完整目录 | ❌ 违规 |
