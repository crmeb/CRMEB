# 性能与缓存规范

> 真源为 `backend/crmeb/services/CacheService.php`、`backend/crmeb/basic/BaseJobs.php`、`backend/crmeb/basic/BaseDao.php`。本文件针对"数据量上来才会爆"的问题，属于上线前必查项。

## 一、查询性能（强制）

1. **列表必须分页，禁止无界查询**：所有列表接口走 `page`/`limit`（见 `接口与响应规范.md` 第三节），`limit` 超 `limitMax` 自动截断。禁止 `select()` 全表返回、禁止"先全查再在 PHP 里截断"。
2. **禁止 `SELECT *`**：`BaseDao::selectList()` 的 `field` 默认是 `'*'`，业务调用**必须显式传字段**，只取需要的列，避免大字段（`text`/`json`/快照）无谓传输。
3. **禁止 N+1 查询**：循环内不得逐条查询关联数据。用 `whereIn` 批量查、`with()` 预加载关联，或一次性查出后内存组装。
4. **禁止循环内写库**：批量写用 `insertAll`/`saveAll` 或事务内批量提交，禁止 for 循环里逐条 `save()`。
5. **查询条件必须能命中索引**：`where`/`order` 命中的列需有索引（索引约定见 `数据库规范.md`）；禁止在索引列上套函数或表达式（如 `where('FROM_UNIXTIME(add_time)=...')`），会退化为全表扫描。
6. **深度分页要优化**：大偏移（`page` 很大）时避免 `limit 100000,10`，改用"上一页最大 id"/游标方式或先按索引列过滤再取。
7. **统计与列表分离但可复用**：`count` 走独立 `getCount()`，禁止为了拿总数把明细全查出来；高频统计结果应缓存（见第二节）。

## 二、缓存规范（强制）

8. **缓存统一走 `CacheService`**，禁止直接使用 `think\facade\Cache` / Redis 原生客户端；`CacheService` 已统一附带 `crmeb` tag，便于批量清理与降级容错。
   ```php
   CacheService::set($key, $value, $expire);              // 写入（tag 默认 'crmeb'）
   CacheService::remember($key, $callback, $expire);      // 读不到才回源计算
   CacheService::get($key, $default);
   CacheService::delete($key);
   CacheService::clear();                                 // 清空 crmeb tag
   ```
9. **缓存 key 必须有命名规范且可读**：建议 `<模块>:<业务>:<标识>`（如 `order:detail:{$orderId}`、`system:config`），禁止 `md5(serialize($arr))` 这类不可读 key，禁止与其它业务共用裸 key。
10. **写入缓存必须设过期时间**：除系统配置这类明确常驻项外，`expire` 不得为 0（永久）；列表/统计类缓存建议短过期 + 主动失效双保险。
11. **缓存必须可失效**：数据变更后主动 `CacheService::delete()` 对应 key，或清 `crmeb` tag；禁止"只写不删"导致脏数据长期存在。
12. **并发写必须加锁**：抢购、库存扣减、任务唯一性等场景用 `CacheService::lock($key, $fn)`（file 驱动下降级为直接执行）或 `CacheService::setMutex($key, $timeout)` + `delMutex()` 成对使用，用完必须释放。
13. **缓存不能作为唯一数据源**：缓存 miss 时必须能回源计算；不得把无持久化的状态只放缓存（重启即丢）。`CacheService` 读写失败会静默返回 false/null，**调用方必须容忍 miss，不得假设缓存必定命中**。
14. **禁止缓存用户敏感数据明文**，缓存内容同样受 `安全红线.md` 第 10 条约束。
15. **插件缓存必须隔离**：`backend/modules/`、`backend/driver/` 下的插件自有缓存统一使用 `PluginCacheService`，由服务自动添加 `plugin:{canonical-id}:` key 前缀和独立 tag。插件禁止调用 `CacheService::clear()` / `clearAll()` 清理共享缓存池；插件修改核心共享数据时，只能通过核心服务提供的精确失效接口处理对应 key。

## 三、事务规范（强制）

16. **事务范围最小化**：只在必要的写操作外层开启事务，禁止把查询、HTTP 请求、文件/图片处理、队列投递包进长事务。
17. **事务内禁止远程调用**：第三方支付/短信/物流调用放在事务外，避免长事务锁表。
18. **事务内失败必须 `throw`**：catch 后 `return fail` 不会回滚（见 `日志与异常规范.md` 第 6 条）。
19. **避免大事务与批量锁**：大批量更新拆批提交；同事务内多表更新注意加锁顺序一致，降低死锁概率。

## 四、队列与异步（强制）

20. **耗时操作必须异步化**：发短信/推送、生成报表、图片处理、大批量数据同步等走队列 `BaseJobs::dispatch()` / `dispatchSecs()`。
21. **异步任务不能假设"一定异步"**：`dispatch()` 仅在 `sys_config('queue_open') == 1` 且 `cache.driver == redis` 时才真正入队，否则**同步执行**。因此 Job 必须同时满足：
    - 幂等（可能被重试或重复执行）；
    - 可同步执行而不阻塞超时（同步模式下会占用当前请求）；
    - **不依赖"请求上下文"**（如 `request()`、登录用户），异步模式下这些不可用。
22. **注意同步模式的递归防护**：`executeSync()` 用 `static::$executingJobs` 阻止同类 Job 递归调用，Job 内再次 dispatch 自身会被跳过并记 `warning`；设计上不要依赖"自己调自己"。
23. **失败重试依赖框架兜底**：`fire()` 未达次数（默认 3）延迟 60 秒重试，达上限删除并写 `error` 日志；Job 内不要 `exit`/吞异常，否则重试与死信日志失效。
24. **队列任务必须可观测**：关键 Job 记录业务单号/ID，便于按 8 列错误日志回溯（见 `日志与异常规范.md` 第 10 条）。

## 五、上线前自检（强制）

25. 新增/改动功能提交前逐项确认：
    - 列表是否分页且有上限？是否显式指定了字段？
    - 是否存在循环内查询/写库（N+1）？
    - 新增查询条件是否命中索引？是否在索引列上套了函数？
    - 缓存是否规范命名、设了过期、可失效、容忍 miss？
    - 并发写是否有锁？事务是否最小？事务内是否有远程调用？
    - 耗时操作是否异步、Job 是否幂等且不依赖请求上下文？
