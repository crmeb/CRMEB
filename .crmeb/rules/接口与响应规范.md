# 接口与响应规范

> 真源为 `backend/crmeb/utils/Json.php` 与 `backend/app/http/BaseApiExceptionHandle.php`。本文件规定"契约本身长什么样"；契约变更要同步到哪些文件见 `前端规范.md` 第三节。路由定义写法见 `代码规范.md` 第四章，不在此重复。

## 一、响应体结构（强制）

1. **统一响应体固定为 `{status, msg, data}`**，`status` 是业务状态码（**不是 `code`**），HTTP 状态码恒为 `200`。前端只按 body 的 `status` 判断成败。
   ```json
   { "status": 200, "msg": "success", "data": { "list": [], "count": 0 } }
   ```
2. **`status` 约定**：成功 `200`；可预期失败 `400`；鉴权类失败由 `AuthException` 的 code 决定；第三方回调等特殊协议用 `Json::status()` 返回大写 `status`（如 `{status:"SUCCESS", msg, data:{status, result}}`）。
3. **`data` 为 null 时整个字段省略**（`Json::make()` 仅在 `$data !== null` 时写入），前端必须容错 `data` 缺失。
4. **`msg` 必须可读且可国际化**：统一走 `getLang($msg, $replace)`，带参数用 `$replace` 替换（如 `'用户 {name} 不存在'` + `['name' => $userName]`），禁止拼接字符串。
5. **禁止在响应中返回 Model/ORM 实例、资源句柄或未裁剪的整表字段**；`data` 只放前端真正需要的字段，敏感字段（密码、token、完整手机号）按 `安全红线.md` 第 10 条脱敏。

## 二、唯一出口与分层（强制）

6. **所有 HTTP 出口必须走 `app('json')`（`crmeb\utils\Json`）**，禁止手写 `json_encode`/`Response::create`/直接 `return array`。
7. **`success()` / `fail()` 只允许出现在 Controller 出口层**：
   - Controller 层可预判失败 → `return app('json')->fail('xxx')`；
   - **Service / Dao / Model 层禁止 return 响应**，只能返回业务数据，失败一律 `throw`（见 `日志与异常规范.md`）。
   - `make(int $status, ...)` 仅在需要自定义非 200/400 业务码时使用，且必须在注释中说明该码含义。
8. **一个接口只有一个成功出口语义**：同一方法内不允许既 `return success` 又 `echo`/`die`；禁止在 Controller 中直接输出调试内容。

## 三、列表与分页（强制）

9. **列表接口统一返回 `{list, count}`**（`compact('list', 'count')`），`count` 是符合条件的总数，供前端分页；非分页列表场景须显式说明。
10. **分页参数固定为 `page` / `limit`**（由 `config('database.page.pageKey'|'limitKey')` 决定），取参统一走 `BaseService::getPageValue()`，**禁止直接读 `param('page')` 自行计算**。
11. **分页必须有上限**：`limit` 超过 `limitMax` 时按上限截断；未传 limit 时用 `defaultLimit`（默认 10）。禁止无 `limit` 的全量查询（详见 `性能与缓存规范.md`）。
12. **排序参数白名单化**：`order`/`sort` 只能取后端白名单字段，禁止把用户输入直接拼进 `order by`。

## 四、请求与校验（强制）

13. **请求方式必须语义化**：查询 `GET`、新增 `POST`、更新 `PUT`、删除 `DELETE`；禁止用 `GET` 承载写操作，禁止用 `POST` 做纯查询。
14. **所有入参必须校验**：用 Validate 类（`validate([...], '规则')` 或独立 Validate），校验失败由 `ValidateException` 统一转 `status=400`；**禁止只靠前端校验**。
15. **资源归属必须服务端校验**：用户侧接口涉及订单/地址/售后等资源时，先校验 `uid` 归属再操作（见 `安全红线.md` 第 6 条），禁止仅凭传入 id 直读直写。
16. **ID 与分页等数值参数必须显式转型**（`(int)`）并校验范围，禁止把未过滤的字符串直接用于查询。

## 五、异常到响应的映射（强制）

17. 异常统一由 `app/http/BaseApiExceptionHandle.php` 渲染，各端只继承不重复实现：
    - `ApiStatusException` → `json.status(apiStatus, msg, apiData)`；
    - `AuthException` / `AdminException` / `ApiException` / `ValidateException` → `json.make($e->getCode() ?: 400, msg, ...)`；
    - 其它 `Throwable` → `json.fail(msg)`（`status=400`）。
18. **新增端（如新 `*api` 应用）必须继承 `BaseApiExceptionHandle` 并实现 `operatorId()`**，禁止自行拼装异常 JSON，否则日志格式与响应格式会分叉。
19. **`app_debug` 关闭时禁止把堆栈/文件路径/SQL 透出到响应**；调试信息仅 `app_debug=true` 时返回（生产必须关闭，见 `安全红线.md` 第 3 条）。

## 六、契约变更（强制）

20. **接口新增/改字段/改结构必须全链路同步**：后端 route/Controller/Service/Dao/Model + `frontend/admin/src/api` + `frontend/uni-app/src/api` + 菜单权限 + 安装/升级数据。同步清单以 `前端规范.md` 第三节为准。
21. **契约变更必须保持兼容或显式升级**：对外已发布的字段名、类型、`status` 语义不得静默变更；确需破坏性变更时同步升级前端与文档，禁止"后端改了前端没改"。
