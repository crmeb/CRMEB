# 订单中台架构规则

## 架构概述

订单中台是 CRMEB v8 系统的统一订单管理枢纽，汇聚系统中**所有类型的订单**（商品订单、积分订单、会员订单等），提供统一的列表聚合、状态管理和详情入口。

> **说明**：充值模块已迁移至 `modules/marketing/recharge/`，彻底脱离订单中台（不再注册 OrderTypeAdapter，订单号改用 `crmeb\utils\SnowflakeIdGenerator` 生成），不再纳入订单中台体系。

**核心设计理念**：`eb_order_center` 是"索引汇聚表"而非"主表"——只存所有订单类型的通用字段，各插件拥有独立的源订单表和专属业务代码。新增订单类型只需实现 Adapter 并在 `modules/` 下注册，零修改中台代码。

## 关联模型

### 三层关联

```
eb_order_center（订单中台表）
  │
  │  order_no（全局唯一） + source_type（来源类型） + source_id（源表ID）
  │
  ├── 产品类型订单
  │   ├── eb_pt_normal_order   (normal_order)
  │   ├── eb_pt_virtual_order  (virtual_order)
  │   └── eb_pt_cardkey_order  (cardkey_order)
  │
  ├── 活动类型订单（规划中，适配多种产品类型，各自有独立状态体系）
  │   ├── eb_pt_seckill_order     (seckill_order)
  │   ├── eb_pt_combination_order (combination_order)
  │   └── eb_pt_bargain_order     (bargain_order)
  │
  └── 用户增值订单
      ├── eb_store_integral_order  (积分订单)
      ├── eb_member_order          (会员订单，会员购买/卡密领取)
      └── eb_offline_receipt       (线下收银记录，收款单非订单)
```

### eb_order_center 核心字段

| 字段 | 说明 |
|------|------|
| `order_no` | 全局唯一订单号，所有表共享 |
| `source_type` | 来源类型标识，决定去查哪张源表 |
| `source_id` | 源表中的主键 ID |
| `order_category` | 订单大类（`goods`/`points`/`member`） |
| `product_type` | 产品类型（`normal`/`virtual`/`cardkey`/`hotel`/`ticket`） |
| `activity_type` | 活动类型（`seckill`/`combination`/`bargain`/`integral`） |
| `status_code` | 统一状态码（8 种） |
| `pay_status` | 支付状态（0 未付/1 已付/2 部分退/3 全退） |
| `refund_status` | 退款状态（0 无/1 申请中/2 已退） |
| `extra_info` | 扩展信息 JSON（配送、优惠明细等） |

## Adapter 适配器模式

### 核心机制

每种 `source_type` 对应一个 Adapter，负责将源表的业务状态**翻译**为 `order_center` 的统一状态码。

```
源表（各自不同状态字段）
    │
    ▼
Adapter::resolveStatusCode($sourceOrder)  →  status_code（统一8种）
Adapter::resolvePayStatus($sourceOrder)   →  pay_status
Adapter::resolveRefundStatus($sourceOrder)→  refund_status
Adapter::resolveBusinessStatus($sourceOrder) → business_status
```

### 统一状态码

| 状态码 | 含义 | 常量（OrderCenter:: 或 OrderTypeAdapterInterface::） |
|--------|------|------|
| `pending_payment` | 待支付 | `STATUS_PENDING_PAYMENT` |
| `processing` | 进行中（已支付，履约中） | `STATUS_PROCESSING` |
| `pending_review` | 待评价（履约完成） | `STATUS_PENDING_REVIEW` |
| `completed` | 已完成（已评价） | `STATUS_COMPLETED` |
| `canceled` | 已取消 | `STATUS_CANCELED` |
| `after_sale` | 售后中（退款/退货/换货/维修） | `STATUS_AFTER_SALE` |
| `refunded` | 已退款 | `STATUS_REFUNDED` |
| `deleted` | 已删除（软删除） | `STATUS_DELETED` |

> `refunding` 为历史兼容值（`@deprecated`，用 `after_sale` 替代），保留用于兼容历史数据。

### 适配器接口

接口文件：`backend/crmeb/trade/order/type/OrderTypeAdapterInterface.php`

```php
interface OrderTypeAdapterInterface
{
    public static function getSourceType(): string;       // 源类型标识
    public static function getOrderCategory(): string;     // 订单大类
    public static function getOrderCategoryLabel(): string; // 大类中文名
    public static function getModelClass(): string;        // 源表模型类名

    public function resolveStatusCode(array $sourceOrder): string;
    public function resolvePayStatus(array $sourceOrder): int;
    public function resolveRefundStatus(array $sourceOrder): int;
    public function resolveBusinessStatus(array $sourceOrder): ?array;

    public function getStatusButtons(string $statusCode): array; // 状态按钮
    public function getOrderButtons(array $detail): array;       // 操作按钮
    public function getProgress(array $detail): array;           // 生命周期进度条
}
```

> 状态码/支付状态/退款状态等常量定义在接口中（`STATUS_MAP`/`PAY_STATUS_MAP`/`REFUND_STATUS_MAP`），`OrderCenter` 模型通过常量委托引用，保证单一数据源。

## 已注册的订单类型

### 产品类型订单（已实现）

| sourceType | 源表 | Adapter | 注册位置 | 大类 |
|------------|------|---------|---------------------|------|
| `normal_order` | `eb_pt_normal_order` | `NormalOrderAdapter` | `modules/product/normal/App.php`（boot） | goods |
| `virtual_order` | `eb_pt_virtual_order` | `VirtualOrderAdapter` | `modules/product/virtual/App.php`（boot） | goods |
| `cardkey_order` | `eb_pt_cardkey_order` | `CardkeyOrderAdapter` | `modules/product/cardkey/App.php`（boot） | goods |

### 活动类型订单（规划中，待从旧 eb_store_order 迁移）

活动订单的核心特点：**适配多种产品类型**（normal/virtual/cardkey），且各自有**独立的订单状态体系**。

| sourceType | 源表（规划） | Adapter（规划） | 注册位置（规划） | 大类 | 特有状态 |
|------------|------------|----------------|----------------|------|---------|
| `seckill_order` | `eb_pt_seckill_order` | `SeckillOrderAdapter` | `modules/trade/seckill/App.php` | goods | 与普通商品一致（待发货/待收货），有限时支付 |
| `combination_order` | `eb_pt_combination_order` | `CombinationOrderAdapter` | `modules/trade/combination/App.php` | goods | 拼团中 → 拼团成功/拼团失败，失败自动退款 |
| `bargain_order` | `eb_pt_bargain_order` | `BargainOrderAdapter` | `modules/trade/bargain/App.php` | goods | 与普通商品一致（待发货/待收货） |

> 活动订单表的 `resolveBusinessStatus` 需要体现活动特有状态。例如拼团的"拼团中"状态通过 `business_status` 返回 `{code: 'pinking', text: '拼团中'}`，但 `status_code` 仍映射为 `processing`。

### 活动订单表与产品类型的关联

活动订单表通过 `product_type` 字段标记底层产品类型，下单时调用对应产品类型的 Handler 处理履约：

```
eb_order_center
  │  source_type = 'combination_order'
  │  product_type = 'normal' / 'virtual'
  │  activity_type = 'combination'
  │
  └── eb_pt_combination_order（活动订单表）
        │  order_no + activity 特有字段（combination_id, pink_id, pink_status）
        │  product_type 字段 → 路由到对应产品 Handler 处理发货/履约
        │
        └── eb_pt_normal_order / eb_pt_virtual_order（产品履约表，可选关联）
```

| sourceType | 源表 | Adapter | 注册位置 | 大类 |
|------------|------|---------|---------------------|------|
| `integral_order` | `eb_store_integral_order` | `IntegralOrderAdapter` | `modules/trade/integral/App.php`（boot） | points |

## 注册器机制

### OrderTypeRegistry

文件：`backend/crmeb/trade/order/type/OrderTypeRegistry.php`

静态注册表模式，内部维护 `static $adapters = [sourceType => adapterClass]` 映射表。各模块在 `App.php` 的 `boot()` 中调用 `OrderTypeRegistry::register()` 完成注册。

**关键方法**：

| 方法 | 说明 |
|------|------|
| `register(string $sourceType, string $adapterClass)` | 注册适配器 |
| `getAdapter(string $sourceType)` | 获取适配器实例 |
| `resolveStatusCode(string $sourceType, array $sourceOrder)` | 推导统一状态码 |
| `getCategoryMap()` | 聚合所有已注册分类信息 |
| `getCategoryBySourceType(string $sourceType)` | 按源类型获取订单大类 |
| `getRegisteredSourceTypes()` | 获取所有已注册源类型 |

### 注册示例

在模块 `App.php` 的 `register()` 中注册：

```php
use crmeb\trade\order\type\OrderTypeRegistry;

// 在 register() 中
OrderTypeRegistry::register('normal_order', \modules\product\normal\handler\NormalOrderAdapter::class);
```

## 状态推导示例

以 `NormalOrderAdapter` 为例，源表字段到统一状态码的映射优先级：

```
源表字段判断                          → 统一状态码
is_cancel == 1                       → canceled
refund_status == 2                   → refunded
refund_status == 1                   → refunding
paid == 0                            → pending_payment
status ∈ {0, 1}                      → processing
status ∈ {2, 3, 4}                   → completed
```

不同订单类型的源表字段和映射逻辑不同（如积分订单的 `status` 值含义不同），各自 Adapter 独立实现。

## 生命周期流程

```
1. 用户下单
   ├── 各模块 OrderCreateServices.createOrder()
   │       ├── 写源订单表（eb_pt_normal_order / eb_store_integral_order / ...）
   │       └── 写 eb_order_center（OrderCenterServices.createRecord()）
   │             └── 通过 Adapter 推导初始 status_code

2. 支付/发货/退款 等事件触发
   ├── 更新源订单表状态
   └── OrderCenterServices.syncStatus(orderNo, statusCode)
         └── 同步更新 eb_order_center 状态

3. 后台/用户端 查询订单
   ├── 列表：直接查 eb_order_center（无需跨表 JOIN）
   │       └── 通过事件 OrderCenterListExtend 注入各模块扩展数据
   └── 详情：eb_order_center 基础数据 + Adapter 实时推导状态
           ├── loadSourceOrderInfo() → 从扩展表读数据，Adapter 重新推导 status_code
           └── loadOrderItems() → 加载商品明细
```

## 关键约束

> **本节是本文的强制条款（违反即缺陷）**，上文各章节的清单与示例仅作参考定位。

1. **状态是"推导"而非"纯粹存储"** — 详情页会通过 Adapter 从源表实时重新推导 `status_code`，确保与源表一致性
2. **`app/` 层不直接引用 `modules/` 层** — 通过 `OrderTypeRegistry` + Adapter 的 `getModelClass()` 声明模型类，避免跨层引用
3. **新订单类型零侵入中台** — 新增只需：创建源表 → 实现 Adapter → 在 `modules/` 下 `App.php` 注册，不修改中台代码
4. **活动订单适配多种产品类型** — 拼团/砍价/秒杀的订单表通过 `product_type` 字段标记底层产品类型，下单和履约时路由到对应产品 Handler 处理，不耦合特定产品类型
5. **活动特有状态不进 `status_code`** — 通过 Adapter 的 `resolveBusinessStatus` 返回活动特有状态（如"拼团中"），`status_code` 保持 8 种通用状态不变
