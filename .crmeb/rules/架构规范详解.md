### 模块内部目录规范（modules/ 各模块统一）

每个模块（`{域}/{type}/`）内部子目录命名与职责**全 modules 统一**，完整三张表见 `backend/modules/README.md`「模块内部目录规范」章节，此处为速查版：

- **根文件（必备）**：`App.php`（模块注册入口）/ `Installer.php` / `plugin.json` / `event.php` / `Handler.php`（产品类型主处理器，实现 `ProductTypeHandlerInterface`，仅 `product/` 域模块有）
- **子目录（按需，命名固定）**：`controller/`（`admin/` + `user/v1/` 双端）、`route/`（`admin.php`/`user.php`，自动扫描加载）、`service/`、`dao/`、`model/`、`validate/`、`listener/`、**`jobs/`（复数，队列任务，继承 `BaseJobs`；单数 `job/` 已废弃，2026-08 统一迁移，禁止新建）**、`handler/`（`trade/` 域放 `{Mode}ActivityHandler`；`product/` 域放 `{Type}OrderAdapter` + `{Type}AfterSaleHandler`）、`crontab/`

## 消息通知架构

消息通知系统采用**门面直调 + 渠道适配器**设计，严格遵循三层架构依赖方向。
渠道选择、适配器实例化、投递与日志全部在 app 层 `Notice` 门面完成；
crmeb 核心层只提供接口契约与值对象，不再有独立发送管线与注册中心。

### 核心契约（crmeb/services/notice/）

位于 crmeb 核心层，不含任何 app 依赖：

| 文件 | 职责 |
|------|------|
| `NoticeChannelInterface.php` | 渠道接口：`send(NoticeMessage): void` + 渠道声明静态方法（channelKey/channelName/getExtraFields/getSupportScope） |
| `NoticeMessage.php` | 待投递消息值对象（readonly：mark/uid/title/content/variables/extra）；扩展字段只加属性，渠道实现零改动 |
| `AbstractNoticeChannel.php` | 适配器基类：`renderPlaceholders()` 占位符渲染等通用能力 |

渠道发送失败统一抛 `crmeb\exceptions\NoticeSendException`（消息即原因），由门面捕获记日志，不中断其他渠道。

### 渠道适配器

app 层渠道（`app/services/message/channel/`，继承 crmeb 的 `AbstractNoticeChannel`）：

| 渠道 | 依赖 | 说明 |
|------|------|------|
| `SystemChannel` | app\NoticeServices | 站内信，写 eb_notice 表；uid=0 经 AdminNoticeRecipientResolve 事件发客服 |
| `SmsChannel` | app\SmsDriverServices + crmeb\sms\Sms | 短信；`pushSms()` 兼供验证码直接调用 |
| `EmailChannel` | app\EmailDriverServices + crmeb\email\Email | 邮件；`sendEmail()` 兼供外部直接调用（AI 助手/MCP） |
| `DingTalkChannel` | crmeb\bot\Bot | 钉钉机器人，纯调 driver |
| `EntWechatChannel` | crmeb\utils\Http | 企业微信机器人，纯调 driver |

modules 层渠道：`modules/channel/wechat_mp/service/WechatTemplateListService`（is_wechat 公众号模板消息）、`modules/channel/wechat_mini/service/RoutineTemplateListService`（is_routine 小程序订阅消息）。两者经后台配置的 `key_list` 把扁平业务变量映射为微信模板字段。

### 渠道登记（eb_notice_channel）

渠道表是渠道唯一登记处：`channel_key`、`adapter_class`（适配器类名）、`owner_plugin_id`、`support_user/support_platform`、`status`（全局开关）、`config`。核心安装 SQL 与插件 Installer 种子写入。发送时按 `adapter_class` 实例化（`class_exists` 校验），并按 `owner_plugin_id` 校验归属模块启用状态（`ModuleStateChecker::isOwnerActive`），禁用/卸载插件的渠道不投递。管理端渠道列表、通知就绪判断（`NoticeConfigServices::adapterRegistered`）同源读取渠道表。

### 为什么渠道实现不在 crmeb/services/notice/channel/

`crmeb/` 不可调用 `app/`（架构铁律）。SystemChannel/SmsChannel/EmailChannel 的核心逻辑依赖 app 层服务（写站内信表、读驱动配置），若放进 crmeb 即违规。DingTalk/EntWechat 虽无 app 依赖，但与三者统一放 app 层更简单一致。app 层调 crmeb 的 Bot/Http/Sms/Email 驱动是合法的（app 可调 crmeb）。

### 调用链

```
业务代码 → Notice::to($uid)->channel('is_sms')->sendMsg($mark, $name, $data)
         → 核心安装 SQL / 插件 Installer 预先登记 (mark,type)
         → SendNoticeService::getNoticeInfo（带缓存查配置，channels 含渠道表合并字段）
         → Notice::selectTargets（纯过滤：type 匹配 + 渠道开关 + 支持范围 + 归属启用 → NoticeMessage 待投递清单）
         → Notice::deliver（逐渠道：实例化 adapter_class → 渠道.send(NoticeMessage) → 写 eb_notice_log）
         → 返回 [channel_key => ['success' => bool, 'error' => string]]；空数组 = 没有渠道实际执行
```

### 消息初值与插件归属

- 核心消息、内置渠道定义写入 `backend/public/install/data/`（`notice_config_data.sql` / `notice_channel_data.sql` / `notice_template_data.sql`，渠道行含 `adapter_class`）；`BaseModuleInstaller` 的 `getNoticeDefinitions()` / `getNoticeChannelDefinitions()` 默认返回空数组，插件在所属现有 Installer 覆写对应方法，`seed()` 调用 `NoticeSeedServices::seed()` / `seedChannels()` 登记返回的数据，不另建消息声明文件。
- `eb_notice_config.owner_plugin_id` 与 `eb_notice_channel.owner_plugin_id` 使用 canonical 插件 ID；相同 `(mark,type)` 或 `channel_key` 的空归属行可由所属 Installer 条件认领，只补空字段，不覆盖已编辑配置。已有其他所有者占用时安装报错。通知模板跟随所属配置 ID 卸载，历史站内信、已读状态与发送日志保留；被其他插件引用的渠道定义保留。
- 插件禁用时保留配置但停止投递，启用时幂等补种；重复种子只补缺失及空值，保持后台改过的开关、标题、模板和商户凭据。
- `to($uid)` 使用 type=1，`to(0)` 使用 type=2；同 mark 双侧必须分别种两条配置。外部渠道预填文案及短编号但默认关闭，核心短信验证码 `verify_code/type=1/is_sms` 例外：安装 SQL 中默认开启，后台不得关闭该模板或短信渠道的全局开关/用户端支持。商户 `tempid` 留空，其他外部模板开启前检查模板、收件人、适配器与渠道全局开关。
- 后台列表不再逐文件扫描，未知 mark 的发送不再落库。变量与场景由监听器实际调用核对后写入 Installer；动态发货的 `order_postage_success` 和 `order_deliver_success` 分别声明。

### 新增渠道

1. 在 `app/services/message/channel/` 创建 `XxxChannel extends AbstractNoticeChannel`，实现 `send(NoticeMessage $message): void`（成功直接返回，失败抛 `NoticeSendException`）；modules 层渠道放各自模块 `service/` 目录
2. 渠道定义登记 `adapter_class`：核心渠道写入 `public/install/data/notice_channel_data.sql`，插件渠道在所属 Installer `getNoticeChannelDefinitions()` 返回定义（含 `adapter_class`），`seedChannels()` 幂等补种
3. 后台从渠道表读取渠道清单与就绪状态；发送时按渠道表 `adapter_class` 实例化并校验归属模块启用状态

## 模块注册机制

各模块通过 `App.php` 的 `register()` / `boot()` 完成扩展点注册：

```php
// app/AppService.php（register() 中向容器注入注册器单例）
$this->app->instance(ProductTypeRegistry::class, new ProductTypeRegistry());

// modules/product/normal/App.php（子模块：注册具体 Handler）
class App
{
    public static function register(ThinkApp $app): void
    {
        // 获取容器中的注册器单例，注册 Handler
        $registry = $app->make(ProductTypeRegistry::class);
        $registry->register('normal', \modules\product\normal\Handler::class);
    }

    public static function boot(ThinkApp $app): void
    {
        // 加载本模块事件监听器
        $eventFile = __DIR__ . '/event.php';
        if (is_file($eventFile)) {
            $event = include $eventFile;
            if (is_array($event)) {
                $app->loadEvent($event);
            }
        }
    }
}
```

### 注册机制（事件驱动）

系统采用**事件驱动注册**，`app/AppService.php` 的 `boot()` 阶段触发 3 个注册事件，由 `app/listener/system/` 下的监听器和各模块监听器分别注册扩展点。新增扩展点只需在对应模块加监听器，无需修改 `AppService`。

```php
// app/AppService.php
public function register()
{
    // 注册中心绑定为容器单例
    $this->app->bind(TradeModeRegistry::class, function () {
        return new TradeModeRegistry();
    });
}

public function boot()
{
    // 模块扫描注册（执行各模块 App::register()/boot()，加载模块事件）
    PluginManager::register($this->app, $basePath . 'modules/');
    $moduleRegistry->registerAll($basePath . 'modules/');

    // 创建注册中心单例
    $tradeModeRegistry = $this->app->make(TradeModeRegistry::class);

    // 统一触发注册事件，app 层与 modules 层监听器各自注册
    event('OrderTypeRegister');
    event('TradeModeRegister', ['registry' => &$tradeModeRegistry]);
}
```

```php
// app/listener/system/TradeModeRegisterListener.php
public function handle($event): void
{
    $registry = $event['registry'];
    // 普通购买（框架默认，不可移除）
    $registry->register('normal', \crmeb\trade\DefaultTradeModeHandler::class);
    // 会员交易模式（位于 app/services/user/member/）
    $registry->register('member', \app\services\user\member\MemberTradeModeHandler::class);
}
```

各 `modules/trade/{type}/App.php` 在 `register()` 中调用 `$registry->register('{type}', Handler::class)` 注册秒杀/拼团/砍价/积分等模式。

### 四大注册中心

| 注册中心 | 位置 | 职责 | 注册时机 |
|---------|------|------|---------|
| `TradeModeRegistry` | `crmeb/trade/mode/` | 交易模式（normal/member/seckill/combination/bargain/integral） | `TradeModeRegister` 事件 |
| `ProductTypeRegistry` | `crmeb/trade/product/` | 产品类型（normal/virtual/cardkey） | 各 `modules/product/{type}/App.php` register() |
| `OrderTypeRegistry` | `crmeb/trade/order/type/` | 订单类型适配器（source_type → 状态适配器） | `OrderTypeRegister` 事件 |

> 消息通知渠道已不走注册中心：渠道适配器类名登记在 `eb_notice_channel.adapter_class`，由 `Notice` 门面按表实例化（见「消息通知架构」）。

> **演进说明**：`crmeb/plugin/ExtensionRegistry` 是统一注册中心的演进方向，逐步替代分散的 Registry。当前 `ProductTypeRegistry` 仍大量使用，过渡期内多 Registry 并存。

`TradeModeRegistry` 与 `TradeModeHandlerInterface` 承接旧活动注册机制的职责；当前契约已继续演进，开发时必须以 `backend/crmeb/trade/mode/` 下的现行接口为准，不按旧接口方法数或历史类名推断。

### 插件间共享表准入协议（强约束）

多插件共用的数据表（如 `eb_store_activity` 活动通用表）不是任何单一插件的自有表，其结构性操作必须走协议，防止某插件卸载时单方面 DROP 或清空他人数据：

1. **目录准入**：可共享的表必须先登记在 `BaseModuleInstaller::SHARED_TABLE_CATALOG`（核心层白名单），目录外表禁止插件间共享。
2. **声明准入**：使用共享表的插件 Installer 必须覆写 `sharedTables()` 声明表名；声明目录外的表会在安装时抛异常。
3. **登记/释放**：安装与启用时框架自动登记到 `eb_shared_table_registry`（`uk_table_plugin` 幂等），卸载时自动释放，插件无需手写。
4. **仲裁删表**：卸载 `rollbackMigrate()` 中删除共享表必须调用 `dropSharedTableIfUnclaimed($table)`（无任何插件占用登记才 DROP），禁止裸 `exec("DROP TABLE ...")` 删目录内共享表。
5. **数据清理边界**：`cleanTable()` 清理共享表必须携带归属条件（如 `['type' => 1]`）只删本插件数据行，无条件全表清空一律拒绝。

协议设施（目录、登记表、仲裁 API）全部位于核心层 `crmeb/module/BaseModuleInstaller.php`，插件层零核心代码改动即可接入。

## 价格链与促销计价扩展点

订单计价采用固定段位价格链，段位契约固化在 `crmeb/services/price/PriceChainPriority.php`（crmeb 核心底层，中台与插件共同引用）：

| 段位 | 名称 | 实现 |
|------|------|------|
| [10] | 会员价 | SKU truePrice 阶段折算进入计价基数 |
| [20] | 促销优惠 | **扩展缝口**：`OrderPromotionCompute` 事件（满减/满赠/加价购等交易营销插件挂载点） |
| [30] | 优惠券 | 中台内置 `OrderComputedServices::useCouponId()` |
| [40] | 积分抵扣 | 中台内置 `useIntegral()` |
| [50] | 会员权益 | 预留 |
| [90] | 运费 | 中台内置 `computedPayPostage()`（独立于商品金额优惠链） |

### 促销计价缝口（OrderPromotionCompute）

- 触发位置：`app/services/order/OrderComputedServices.php::applyPromotion()`，位于优惠券段之前；秒杀/拼团/砍价等活动单（`$isActivity`）不触发
- 写回契约（监听器返回 void，改引用变量）：`$event['promotion_price']` 累加写回优惠总额；`$event['detail'][插件标识]` 写回明细数组（如 `['title' => '满100减20', 'price' => 20]`）；中台做边界保护（不为负、不超过商品总价）
- 结果流向：`promotion_price` / `promotion_detail` 进入计价结果数组 → 结算预览 → 创建态缓存校验 → `OrderCreateAfter` 的 `price_data` 快照
- 与展示层互补：价格明细展示行注入走 `OrderPricingExtend`（仅展示不计价），金额计算一律走本事件

> 二开准则：营销玩法禁止在 app 层实现或硬编码营销金额；一律以 `modules/marketing/{type}` 模块 + 本事件接入，插件未安装时缝口为空操作。

## 模块路由自动加载机制

模块路由文件放入 `modules/{module}/route/` 目录后，系统会自动扫描加载，**无需手动 `include`**。

### 扫描规则

```php
// 在对应入口文件中通过 glob 自动扫描
foreach (array_merge(
    glob(root_path() . 'modules/*/route/{file}.php') ?: [],    // 一级模块
    glob(root_path() . 'modules/*/*/route/{file}.php') ?: []   // 二级模块
) as $file) {
    require $file;
}
```

### 端口映射

| 入口文件 | 扫描文件名 | 端口用途 |
|---------|-----------|---------|
| `app/adminapi/route/route.php` | `route/admin.php` | 后台管理端（PC管理后台） |
| `app/api/route/v1.php` | `route/user.php` | 用户端（小程序/H5/公众号） |
| `app/kefuapi/route/route.php` | `route/manage.php` | 移动管理端（商家手机端） |
| `app/outapi/route/route.php` | `route/outapi.php` | 开放平台接口（第三方对接） |

### 模块路由文件示例

```php
// modules/product/normal/route/admin.php
use think\facade\Route;
use app\http\middleware\AllowOriginMiddleware;
use app\adminapi\middleware\AdminAuthTokenMiddleware;

Route::group('normal', function () {
    Route::get('product/list', [\modules\product\normal\controller\admin\ProductController::class, 'list']);
    Route::post('product', [\modules\product\normal\controller\admin\ProductController::class, 'save']);
})->middleware([
    AllowOriginMiddleware::class,
    AdminAuthTokenMiddleware::class,
])->option(['mark' => 'normal', 'mark_name' => '实物商品管理']);
```

### 目录结构示例

```
modules/product/normal/
├── route/
│   ├── admin.php      # 后台管理端路由（自动加载）
│   ├── user.php       # 用户端路由（自动加载）
│   └── manage.php     # 移动管理端路由（自动加载）
├── controller/
├── service/
├── dao/
├── model/
├── App.php
├── event.php
└── Handler.php
```

**注意**：
- 路由文件中的中间件**必须自行引入**，系统不自动添加
- 新增模块只需在 `route/` 下放对应文件，**无需修改任何入口文件**
- 模块路由与 `app/` 层路由互不干扰，系统会合并注册

## 前端经验记录

### `defineSwitch` 开关文字跑偏

**现象**：使用 `class="defineSwitch"` + `active-text`/`inactive-text` 的 `<el-switch>`，如果所在 `<el-table-column>` 加了 `align="center"`，文字绝对定位会错位。

**原因**：`defineSwitch` 全局 CSS 使用 `position: absolute` 定位开关内的文字，`align="center"` 会干扰绝对定位的参照坐标。

**修复**：去掉列上的 `align="center"` 即可：

```html
<!-- ❌ 错误 -->
<el-table-column label="状态" width="120" align="center">

<!-- ✅ 正确 -->
<el-table-column label="状态" width="120">
```
