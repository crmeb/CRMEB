# 后端架构规则（精简常驻版）

> **完整架构内容**（目录结构树、模块注册机制、消息通知架构、第三方驱动后台管理规范、模块路由自动加载机制、系统配置菜单路径规范、前端经验记录、规则变更维护说明）见 [架构规范详解.md](架构规范详解.md)（`alwaysApply: false`，按需加载）。本文件是常驻精简版，只保留高频约束。

## 架构概述

v8.0 采用**三层架构**，依赖方向单向、不可逆：

```
modules/（业务扩展层）→ app/（统一管理中台）→ crmeb/（核心底层）→ driver/（第三方驱动底座）
```

**没有 `common/` 层**：旧版的 `common\App.php` 统一调度入口已废弃。

## 依赖铁律（强约束）

| 层 | 可以调用 | 不可以调用 |
|----|---------|-----------|
| `modules/` | `crmeb/`、`app/` | —— |
| `app/` | `crmeb/` | ❌ 绝不可反向调用 `modules/` |
| `crmeb/` | `driver/` | ❌ 不可调用 `app/`、`modules/` |
| `driver/` | （仅自身） | ❌ 只能被 `crmeb/services` 调用 |

## 5 个高频违规点（必须规避）

1. **app/ 层引用 modules/ 类（反向调用）**：`app/` 不能 `use` 任何 `modules/` 下的类，业务扩展层的数据或行为应由扩展点注册的事件监听器处理。
   ```php
   // ❌ use modules\channel\wechat_mp\service\WechatUserServices;
   // ✅ event('OrderCreateAfter', ['order_id' => $orderId]);
   ```
2. **硬编码业务数据映射表**：支付方式、配送方式、发票类型等可枚举但会随驱动扩展而变的数据，必须从 `eb_pay_channel` 等配置表动态读取，禁止硬编码。
3. **modules/ 下跨模块互引**：各扩展点（trade / marketing / channel）相互独立、不可感知，跨模块通信一律走 crmeb 核心层契约或事件；引用自身模块层次结构（如 `modules/product/normal/Handler`）允许。
4. **残留无用 `use` 语句**：移除跨层或跨模块调用后必须同步清理 `use`。检查方法：搜索该 `use` 的短类名，确认无 `new` / `::` 静态调用 / `app()->make()` / 类型声明等实际调用。
5. **中台层处理扩展层独有字段**：商品/订单中台（`CenterProductServices`、`OrderCenterServices`）及对应控制器，不得直接处理 `modules/` 层扩展独有的业务字段，应触发 `OrderCenterDetailExtend` / `ProductDetailExtend` 等事件由扩展监听器处理。
   > 判断标准：`extra_info`/`custom_form` 的 JSON 存储是中台的正当职责；**从中台提取特定 key 到顶层并 unset** 属于扩展层业务逻辑，必须放在扩展模块的监听器中。

## 4 大扩展点

| # | 扩展点 | 解决什么 | 落地位置 |
|---|--------|---------|---------|
| 1 | **产品类型** | 卖什么/库存/运费/履约流程 | `modules/product/{type}/` |
| 2 | **交易模式** | 怎么卖/定价/验证/售后规则 | `modules/trade/{type}/` |
| 3 | **用户渠道** | 用户从哪来/如何识别登录 | `modules/channel/{端}/` |
| 4 | **营销玩法** | 抽奖/直播/签到等运营活动 | `modules/marketing/{type}/` |
| – | 支付方式（基础设施） | 怎么收钱/退款对账 | `driver/pay/` |

交易模式是订单创建的**主维度**，产品类型是**子维度**。产品类型通过 `getCompatibility()` 声明支持的交易模式（normal → normal/virtual/cardkey/hotel/ticket；seckill → normal/virtual；combination/bargain/advance/integral → normal），交易模式注册中心获取处理器时校验兼容性。

## 事件调用规范

```php
// ✅ 正确：字符串 key 名称（服务层统一无 Listener 后缀，如 OrderPaySuccess / OrderCancel / OrderCreateAfter）
event('OrderPaySuccess', [$orderId]);

// ❌ 错误：不要使用类常量
event(OrderPaySuccess::class, [$orderId]);
```

## 代码注释规范（强约束）要点

- 每个类必须包含 PHPDoc 描述；所有 public/protected 方法必须有 PHPDoc（含 `@param`/`@return`）；类属性必须有 `@var` 说明注释
- 复杂业务逻辑前添加中文单行注释说明意图；条件分支/循环/闭包要注释其作用；hack/临时方案必须标注原因
- 注释统一使用**中文**
- **业务监听器 `Notice::sendMsg()` 调用处**：语句上方写 `// 场景：xxx`，业务变量行尾写中文描述；核心通知初值由安装 SQL 登记，插件通知 `(mark,type)`、场景、变量、默认模板在现有 Installer 覆写 `getNoticeDefinitions()`，插件渠道定义覆写 `getNoticeChannelDefinitions()`，均由 `seed()` 登记、卸载按归属清理。基类两个方法默认返回空数组。不得依赖发送或列表请求自动建档，不另建 `notice.php`。接收者即类型：`to($uid)` 为用户，`to(0)` 为平台客服（双侧通知同 mark 各调一次）。详见《架构规范详解.md》「消息初值与插件归属」。

## 二开扩展范式

1. **写扩展实现**：在对应扩展点目录创建 Handler/子模块
2. **建扩展表**：扩展业务字段 + 登记到字典/配置表
3. **注册登记**：在模块 `App.php` 追加注册
4. **完成**：0 修改核心代码

## 数据库变更规范（强约束）

**修改数据库（建表/改表/增删改数据）后，必须同步更新安装 SQL，否则全新安装的站点将缺少该变更。**

安装 SQL 位于 `backend/public/install/`，安装时合并执行：

| 变更类型 | 同步更新的安装 SQL 文件 |
|---------|----------------------|
| 表结构 | `crmeb_table.sql` |
| 系统配置项 | `backend/public/install/data/*_data*.sql` |
| 系统配置分组（tab） | `backend/public/install/data/*_data*.sql` |
| 后台菜单 | `backend/public/install/data/*_data*.sql` |
| 字典/分类/协议等中小表数据 | `backend/public/install/data/*_data*.sql` |
| 其他核心初始数据 | `backend/public/install/data/*_data*.sql`（语言/快递/城市/附件/路由等） |

- `crmeb.sql.bak` 是**原始完整备份文件，不参与安装执行，禁止修改**。
- 更新安装 SQL 时保持 INSERT 行格式与原始文件一致（字符串内 `\n`/`\"` 等转义需保留）。
- 更新后需验证：安装 SQL 无残留记录、本地库与安装 SQL 保持一致。
- **模块自有数据不预置核心安装 SQL**：模块的菜单、系统配置 tab、配置项应由模块 `Installer.php` 负责创建（`getMenuConfig()` + `seed()`，卸载由 `cleanData()` 清理），核心安装 SQL 只保留与模块无关的系统级数据。

## 当前发布阶段（强约束）

- **当前处于首版开发阶段，尚无已发布版本或存量站点**：所有插件清单及 Installer 版本统一为 `1.0.0`，功能修复和新增能力不提升插件版本号。
- **所有改动直接纳入首次安装定义**：核心数据更新安装 SQL，插件自有结构、菜单和种子更新 Installer；不新增升级脚本、旧版本数据转换或仅为升级保留的兼容分支。通知 Installer 仅按准确 `(mark,type)` 条件认领已有空归属配置、按准确 `channel_key` 条件认领已有空归属渠道，属于种子幂等处理，不扩大为通用迁移。
- 安装、种子、启用与禁用仍须幂等；首版约定不豁免安全边界与全新安装验证，也不授权执行真实数据库安装或迁移。
- 本节优先于 rules/skills 中面向存量站点的通用升级说明；只有用户明确进入发布后的维护阶段时，才恢复版本递增与升级链要求。现有通用升级设施不因此整体删除。

## 数据库连接环境

直接查询数据库时，默认读取 `backend/.env` 的实际连接配置，不得假定 Docker 容器名或映射端口，也不得为了查询而自动启动容器。

- 宿主机本地 MySQL 通常使用 `127.0.0.1:3306`，具体以 `.env` 为准。
- 只有用户明确选择根 Compose 环境或目标库已运行在该环境时，宿主机工具才使用 `127.0.0.1:33061`。
- 数据库名、用户名与密码均从本地配置读取，不把文档示例值当作当前凭据。

```bash
mysql -h <hostname> -P <port> -u <username> -p <database>
```
