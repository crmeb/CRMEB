# 目录与文档规范（单一真源）

> 本文件是目录职责与文档归属的唯一出处。`.crmeb/AGENTS.md` 规则索引、`tests/README.md` 只引用本文，不复制条款；修改目录约定只改这里。

## 一、三类知识目录职责边界（强制）

| 目录 | 定位 | 内容范围 | 生命周期 |
| --- | --- | --- | --- |
| `help/docs/` | 手动维护的**项目说明**（当前事实） | 项目、架构、功能、API、部署、运维 | 长期有效，随代码同步更新 |
| `.crmeb/` | AI 开发**约定真源** | 规则、技能、子智能体、各端 scopes | 长期有效，强制约束 |
| `tests/` | **开发过程文档 + 测试统一入口** | 过程文档（`plans/` 方案、`reports/` 评审与检查报告、`skills/` 可分发治理模板）；测试索引与统一运行编排 | 过程文档有生命周期：实施后转移，失效后删除；索引与模板长期有效 |

## 二、归属判定规则（强制）

自问一句：**这是"当前事实"，还是"过程产物"？**

- 当前事实（项目是什么、怎么跑、接口长什么样）→ `help/docs/`
- 过程产物（打算做什么、检查了什么、评审结论）→ `tests/`（`plans/` 方案、`reports/` 评审与检查报告）
- 强制约定（违反即错误）→ `.crmeb/rules/`；操作手册（怎么做）→ `.crmeb/skills/`
- 一次性产物（调试临时脚本、AI 会话产物、临时报告）→ 不入库，见 [提交规范.md](提交规范.md) 三

## 三、文档登记与引用（强制）

1. `help/docs/文档索引.md` **不得登记** `tests/` 下任何过程文档；两者不互相引用正文。
2. `tests/plans/`、`tests/reports/` 下文档顶部必须标注性质（待评审 / 已实施 / 已归档）与核对日期。
3. 方案评审通过并实施后，已落地内容必须转入对应正式文档（`help/docs/`、`.crmeb/rules/`、`.crmeb/skills/`），过程文档仅保留决策记录；完全失效后删除。
4. 引用规则条款时只放链接，禁止在 `tests/`、`help/docs/` 复制 `.crmeb/` 正文。

## 四、测试脚本归属（强制）

1. **按端落位**：后端 `backend/tests/`；管理端 `frontend/admin/scripts/`；移动端 `frontend/uni-app/scripts/`。根 `tests/` 不存放各端测试脚本，只放索引与编排脚本，以及第一节所列过程文档与可分发模板。
2. **后端测试脚本不入库**：`.gitignore` 忽略 `/backend/tests/`，后端脚本为本地运行件；索引登记是其唯一交付痕迹（见第 5 条）。
3. **禁止物理迁移**：不得把各端测试脚本搬到根 `tests/`——PHP 脚本的 `dirname(__DIR__)` 上溯层级、前端 ESM 静态导入路径与 `node_modules` 就近解析都会被破坏。
4. **禁止复制与软链**：根 `tests/` 不复制测试脚本、不建符号链接（规避 Windows 兼容问题），对测试只做索引与编排。
5. **新增测试必须登记**：在根 `tests/README.md` 补充条目（位置、用途、运行命令、前置依赖），未登记视为未交付；后端脚本不入库，登记条目须完整到协作者可按说明在同位置重建。
6. **测试依赖必须显式声明**：测试用到的第三方包必须写进对应端的 `package.json`（`devDependencies`）或 `composer.json`，禁止依赖传递引入。
7. 命名约定：PHP 回归脚本用 `XxxRegressionTest.php` 并在文件头注释标注"非 PHPUnit，直接 `php` 执行"；Node 测试脚本统一 `test-<域>.mjs`；纯校验工具（如 `check-*.mjs`）属 lint 类，不计入测试索引。

## 五、文档更新流程（强制）

1. 每次新增、修改或删除文档，提交前必须**全量运行检查**：先运行 `php think docs:check` 检查 Markdown、frontmatter、索引与路径，再从仓库根运行 `node scripts/check-doc-facts.mjs` 校验模块/驱动/默认安装/基础表数量及根入口文档链接。前者需 PHP ≥8.2；无本地环境时用项目镜像一次性容器挂载仓库根执行，注意运行中的 compose 容器只挂载 `backend/`，看不到全仓库。
2. error 级问题（死链、frontmatter 违规）必须清零后才能提交。
3. warning 级须逐条确认：属真漂移的当次修复或转立项；属误报的补充豁免并在命令内注明原因，禁止无说明忽略。
4. 修复死链时同步核对目标是否为唯一真源，禁止把链接改向非真源副本。

## 六、冲突处理（强制）

**1. 内容裁决顺序（出现矛盾时以谁为准）**

- 代码实现 > 文档描述：文档与代码行为不一致，以代码为准修文档；无法确认实现意图时先与维护者确认，**禁止按文档反向改代码**。
- 真源 > 引用方：`.crmeb/` 真源与 AGENTS.md 索引、各端 AGENTS.md、`help/docs/` 的转述不一致时，以真源为准修引用方，禁止两边各改各的。
- 专项规则 > 通用规则：条款撞车时 [安全红线.md](安全红线.md) 最高，其次 [插件开发规范.md](插件开发规范.md) 等专项规则，最后通用规范；仍无法裁决时提维护者定夺，并把结论落进胜出条款、清理落败方。

**2. Git 合并冲突（文档并发修改）**

- Markdown 冲突禁止机械整取（`--ours` / `--theirs` 一键覆盖），须按语义合并双方改动。
- 索引表（`.crmeb/AGENTS.md`、`tests/README.md` 等）冲突必须**合并双方新增行**后去重，禁止丢弃任何一方的登记。
- 冲突解决后必须全量重跑 `php think docs:check`，error 清零方可提交（同第五节）。

**3. 本地副本与缓存冲突**

- 工具软链目录（`.claude/`、`.trae/`、`.cursor/` 等被 gitignore 的本地目录）或工具缓存与仓库真源不一致时，一律以真源为准，禁止直接编辑软链内的文件。
- `tests/` 下的过程文档与正式文档矛盾时，以正式文档为准；过程文档按生命周期标注归档或删除。

## 七、与其他规则的边界

- [提交规范.md](提交规范.md) 管**什么不能入库**（密钥、本地环境、临时产物）；本规范管**内容落在哪个目录**。
- [架构规范.md](架构规范.md) 管**代码依赖方向**；本规范不管代码，只管知识资产与测试的位置。
