# 日志与异常规范

> 真源为 `backend/crmeb/exceptions/`、`backend/app/http/BaseApiExceptionHandle.php`。核心坑：**业务异常默认不写日志**，所以"该不该落日志"直接决定你该抛哪个异常。

## 一、异常类选型（强制）

| 异常类 | 命名空间 | 使用场景 | 默认响应 `status` | 是否落日志 |
| --- | --- | --- | --- | --- |
| `AdminException` | `crmeb\exceptions` | 管理端（adminapi）业务规则失败 | 400 | ❌ 不落（`ignoreReport`） |
| `ApiException` | `crmeb\exceptions` | 用户端（api）业务规则失败 | 400 | ❌ 不落（`ignoreReport`） |
| `AuthException` | `crmeb\exceptions` | 登录/token 失效、无权限 | code 或 400 | ❌ 不落（`ignoreReport`） |
| `ValidateException` | `think\exception` | 参数校验失败（框架自动抛） | 400 | ❌ 不落（`ignoreReport`） |
| `ApiStatusException` | `crmeb\exceptions` | 需自定义大写 `status` 的特殊协议（如支付回调） | 自定义 status | ✅ 落日志 |
| `CrudException` | `crmeb\exceptions` | 通用页面（SchemaPage）CRUD 校验失败 | 400 | ✅ 落日志 |
| `BusinessException` | `crmeb\exceptions` | 业务中断，可携带 `errorCode` + `extra` 附加数据 | 400 | ✅ 落日志 |
| `PayException` / `UploadException` | `crmeb\exceptions` | 支付/上传流程失败 | 400 | ✅ 落日志 |
| `OAuthException` | `crmeb\exceptions` | 各端授权/第三方 OAuth 失败，可携带 `raw` 原始响应 | 400 | ✅ 落日志 |

1. **业务可预期失败用 `AdminException` / `ApiException`**，不要用 `\Exception`；**系统级错误（DB 异常、第三方超时、文件不可写）必须 `throw new \Exception`**——因为业务异常在 `ignoreReport` 里不会写日志，用错会导致线上无任何线索。
2. **禁止跨端混用**：管理端逻辑抛 `AdminException`，用户端逻辑抛 `ApiException`；模块代码按所属端选择，不要一律用同一种。
3. **异常消息必须可读且可国际化**，统一经 `getLang()`；带变量用 `$replace`：
   ```php
   throw new ApiException('用户 {name} 不存在', ['name' => $userName]);
   throw new AdminException([400, '订单状态不允许该操作']);
   ```
4. **需要携带业务数据给前端**（如冲突的 order_id）用 `ApiStatusException`，`getApiData()` 会随响应返回：
   ```php
   throw new ApiStatusException(400, '业务错误', ['order_id' => 123]);
   ```

## 二、throw / fail / success 分层规则（强制）

| 场景 | 正确写法 |
| --- | --- |
| 业务成功 | Controller 层 `return app('json')->success($msg, $data)`；Service 层 `return $data` |
| Controller 可预判失败 | `return app('json')->fail('提示')` |
| Service / Dao 深层业务校验失败 | `throw new AdminException(...)` / `throw new ApiException(...)` |
| 事务内失败需回滚 | 必须 `throw`，禁止 `return fail`（否则事务不会回滚） |
| 系统级/未预期错误 | `throw new \Exception(...)`（保证落日志） |

5. **Service / Dao / Model 层禁止 `return success/fail`、禁止返回 Response 对象**，只能返回数据或抛异常（分层要求见 `接口与响应规范.md` 第 7 条）。
6. **事务内禁止吞掉异常后 `return fail`**：一旦 catch 后不重抛，事务提交、数据不一致。
7. **同一失败只抛一次**：禁止在 catch 里重新包装同类异常导致堆栈丢失；需要补充上下文时用 `new XxxException($msg, [], 0, $e)` 透传 `$previous`。

## 三、日志写法（强制）

8. **禁止 `var_dump` / `print_r` / `echo` / `die` / `exit` / `dd` 出现在提交代码中**；调试输出必须走日志。
9. **日志统一走框架 `Log` 门面或助手函数**：
   - 业务过程留痕：`crmebLog($msg)`（写入 `crmeb` 通道）；
   - 分级日志：`Log::info` / `Log::warning` / `Log::error`；
   - 本地临时落盘调试：`debug_file($content, $fileName = 'error')`、`dump_sql()`——**仅限本地排障，禁止留在提交里**。
10. **异常日志格式由 `BaseApiExceptionHandle::writeErrorLog()` 统一拼装为 8 列管道分隔**：`操作者ID | 客户ip | 耗时ms | 请求方法 | 应用 | 路由 | 请求参数 | 报错数据(file/line/message/code)`。新增端必须继承该基类实现 `operatorId()`，禁止自造格式。
11. **日志必须分级合理**：可预期业务失败不要写 `error`；`error` 只留给真正需要排查的问题，避免污染告警。
12. **日志内容必须脱敏**：手机号、身份证、银行卡、密码、token、密钥不得明文写入日志或异常消息（见 `安全红线.md` 第 10 条）。

## 四、catch 与兜底（强制）

13. **禁止空 catch**：`catch (\Throwable $e) {}` 静默吞异常一律禁止；至少 `Log::error(...)` 或重抛。
14. **catch 必须收窄或明确兜底**：优先捕获具体异常类型；捕获 `\Throwable` 时必须有日志 + 明确降级行为（如返回默认值），禁止无差别吞掉后继续执行。
15. **第三方调用失败必须有超时与异常处理**，禁止裸调后假设必定成功；支付、上传、短信等关键链路失败要记录可复盘的请求标识。
16. **队列任务的失败依赖 `BaseJobs::fire()` 兜底**：未达 `errorCount`（默认 3）时延迟 60 秒重试，达上限 `delete()` 并写 `error` 日志。**Job 内部异常不要自行 `exit`/吞掉**，否则重试机制失效。

## 五、排障入口

17. 线上问题优先看 `runtime/` 下 `error` 日志（8 列格式）与业务 `crmeb` 通道日志；异常日志的"应用/路由/请求参数"三列足以定位入口。
18. 新增异常分支时确认：**该失败是否需要留痕？** 需要 → 用会被 report 的类型或显式 `Log::`；不需要 → 用 `AdminException`/`ApiException` 保持日志干净。
