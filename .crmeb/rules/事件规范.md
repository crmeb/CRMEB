# CRMEB v8 系统事件机制文档

---

## 一、概述

本文档整理了 **CRMEB v8** 系统中所有的事件定义、调用机制和扩展指南，为二次开发提供参考。

**事件架构说明**：
- **监听器（Listener）**：事件的具体处理类，实现 `ListenerInterface` 接口
- **通知监听器（XxxNoticeListener）**：消息通知（站内信、短信、微信模板消息等）不再经由统一 `NoticeListener` 入口分发，而是以 `XxxNoticeListener` 监听器直接挂载在对应业务事件上（如 `UserRegister` 事件同时挂 `UserRegisterListener` 业务处理 + `UserRegisterNoticeListener` 通知发送）
- **事件配置**：核心事件注册在 [app/event.php](../../backend/app/event.php)，模块事件注册在各模块的 `event.php` 中

**事件命名规范**：
- 服务层事件名统一使用**大驼峰字符串**，**不带 `Listener` 后缀**
- 监听器类名保留 `Listener` 后缀
- 示例：`event('OrderCreateAfter', [$order])` → 监听器类 `OrderCreateAfterListener`
- 2026-08-18 全量收口后已**无带后缀的历史遗留事件名**（`ProductListener`→`Product`、`UserLevelListener`→`UserLevel`、`NotifyListener`→`Notify` 等均已完成重命名）

**核心优势**：
- 解耦业务逻辑，实现模块间低依赖通信
- 支持同步/异步执行，提高系统响应速度
- 支持多渠道消息通知

> **已下线机制**：旧版 `CustomEventListener`（数据库配置代码执行）与统一 `NoticeListener` 分发入口已从首版代码和安装定义中删除，相关 `eb_system_event` / `eb_system_event_data` 表已退役，禁止在新代码中使用。

## 二、事件调用规范

### 2.1 事件调用格式（强制规范）

**✅ 正确格式（字符串 key 名称方式）**：
```php
// 所有事件均使用字符串 key 名称调用（必须，便于事件扩展）
event('OrderRefundRefuse', [$orderRefundInfo]);
```

**❌ 错误格式**：
```php
// 错误：不要使用类常量方式，这会破坏事件扩展机制
use app\listener\order\OrderRefundRefuseListener;
event(OrderRefundRefuseListener::class, [$orderRefundInfo]);
```

### 2.2 调用规范说明

| 事件类型 | 调用方式 | 原因 |
|---------|---------|------|
| **业务事件** | 字符串 `'EventName'` | 便于事件扩展，支持 event.php 配置覆盖 |
| **通知发送** | 挂载 `XxxNoticeListener` 监听器 | 通知逻辑直挂业务事件，与业务监听器并列注册，无需单独触发通知事件 |

**重要说明**：所有事件调用必须使用字符串 key 名称方式，这是为了支持事件扩展机制。通过 event.php 配置文件可以覆盖或扩展事件监听器，使用类常量方式会破坏这一机制。

### 2.3 事件调用时机

| 调用位置 | 事件类型 | 调用说明 |
|---------|---------|---------|
| **Controller层** | 业务入口事件 | 主要调用核心业务监听器 |
| **Services层** | 业务逻辑事件 | 调用业务处理、通知、推送事件 |
| **Listener层** | 级联触发事件 | 在监听器内部可触发其他事件 |

### 2.4 事件分级与异常隔离（SafeEvent，强制）

框架通过 [app/provider.php](../../backend/app/provider.php) 将容器事件服务重绑为 `crmeb\utils\SafeEvent`（继承 `think\Event`），在逐个调度监听器时自动进行异常隔离与事件分级，`event()` 调用方式完全不变。解决"一个插件监听器抛异常导致下单/支付主流程中断"的稳定性问题。

| 级别 | 范围 | 监听器异常行为 |
|-----|------|-------------|
| **关键（默认）** | 订单/资金/库存等数据一致性事件、注册中心事件、服务代理与查询类事件 | 异常继续上抛，中断主流程（保证数据一致性） |
| **安全事件** | 展示扩展、通知推送、营销旁路、统计记录、渠道同步、定时任务收尾钩子、插件工具注册（McpToolsRegister）（清单见 `SafeEvent::$safeEvents`） | 异常仅 `Log::error` 记录，继续执行后续监听器 |
| **安全监听器（任何事件下）** | 类名以 `NoticeListener` 或 `ExtendListener` 结尾的监听器 | 同安全事件，一律隔离 |

**强制约定**：
1. **旁路职责监听器命名即分级**：通知类监听器类名必须以 `NoticeListener` 结尾（如 `OrderPaySuccessNoticeListener`），展示扩展类监听器必须以 `ExtendListener` 结尾——这是框架识别"旁路职责"并提供异常隔离的唯一依据。
2. **关键监听器异常保持中断**：订单状态推进、库存扣减、资金流水类监听器异常会被正常抛出以保证数据一致性；此类监听器内部对可降级的部分失败应自行 try/catch 并记录日志，但禁止吞掉事务类异常。
3. **安全事件清单收口在 `SafeEvent::$safeEvents`**：新增旁路型事件时同步维护该清单，禁止在业务代码中散落 try/catch 包裹 `event()` 调用。

## 三、事件注册分布

CRMEB v8 采用三层架构，事件监听器分布在核心层和模块层：

### 3.1 核心层（app/event.php）

核心事件注册在 [app/event.php](../../backend/app/event.php)，监听器类位于 `app/listener/` 下。

### 3.2 模块层（modules/*/event.php）

各模块通过自身 `event.php` 注册监听器，系统启动时自动扫描加载（`modules/*/event.php` + `modules/*/*/event.php`）。

**已注册事件的模块清单**：

| 模块 | event.php 位置 | 职责 |
|------|---------------|------|
| product/normal | [event.php](../../backend/modules/product/normal/event.php) | 实物商品订单生命周期 + 售后 + 扩展数据 |
| product/virtual | [event.php](../../backend/modules/product/virtual/event.php) | 虚拟商品订单生命周期 + 售后 |
| marketing/signin | [event.php](../../backend/modules/marketing/signin/event.php) | 签到提醒 + 营销代理 |
| channel/wechat_mini | [event.php](../../backend/modules/channel/wechat_mini/event.php) | 小程序渠道 + 直播 API + 小程序码 |

> 其余已安装模块（如 `aiagent`）当前 `event.php` 为空监听，未注册事件时不入上表；新增监听后同步登记。

### 4.13 通知机制（已收口为监听器直挂模式）

> 旧版统一分发入口 `NoticeListener` / `CustomEventListener` 已从首版代码和安装定义中删除。

```php
// app/event.php：一个事件同时挂业务处理与通知发送两个监听器

```

## 五、最佳实践

### 5.1 事件调用规范

```php
// ✅ 正确示例：所有事件调用使用字符串 key 名称（不带 Listener 后缀）
event('OrderPaySuccess', [$orderInfo]);
event('OrderCancel', [$order, $uid]);
event('ProductDetailExtend', $eventData);
event('Product', ['create', ['id' => $productId]]);  // 单一事件 + type 分发
```

### 5.2 事件参数数组格式规范

**推荐格式（多行数组，每个参数占一行）**：

```php
// ✅ 推荐：多行数组格式，便于阅读和维护
event('UserExpChange', [
    $uid,
    $data['number']
]);

// ✅ 推荐：关联数组每行一个键值对
event('UserBalanceChange', [
    'uid'      => $uid,
    'type'     => $type,
    'amount'   => $amount,
    'balance'  => $balance,
    'mark'     => $mark,
]);

// ✅ 推荐：嵌套数组同样遵循多行格式
event('Product', [
    'status_change', 
    [
        'id'        => $id,
        'oldStatus' => $oldStatus,
        'is_show'   => $is_show,
    ]
]);
```

**不推荐格式**：

```php
// ❌ 不推荐：单行数组，参数过多时难以阅读
event('UserExpChange', [$uid, $data['number'], $data['type'], $data['remark']]);
```

**格式规范要点**：
1. 数组开始括号 `[` 后换行
2. 每个数组元素占一行，缩进 4 个空格
3. 关联数组的键值对冒号 `=>` 后加空格
4. 数组结束括号 `]` 单独占一行
5. 嵌套数组遵循相同格式
6. 参数超过 2 个或包含关联数组时强制使用多行格式

### 5.3 事件设计原则

1. **单一职责**：每个监听器只处理一个业务逻辑
2. **异步优先**：非关键业务使用队列异步处理
3. **错误隔离**：框架层 `SafeEvent` 已按事件分级自动隔离旁路监听器异常（见 2.4）；关键监听器内部对可降级失败仍应自行捕获，禁止依赖框架隔离兜底数据一致性
4. **日志记录**：重要操作添加日志记录，便于排查问题
5. **参数清晰**：事件参数使用关联数组时，键名应清晰表达含义
6. **命名规范**：事件名使用大驼峰，不带 `Listener` 后缀；监听器类名保留后缀

### 5.4 新增事件流程

1. **核心事件**：在 `app/event.php` 的 `listen` 数组中注册事件名和监听器类
2. **模块事件**：在模块的 `event.php` 中注册，系统自动扫描加载
3. **触发事件**：在业务代码中使用 `event('EventName', [$param1, $param2])` 触发
4. **多模块监听**：同一事件名可被多个模块注册，系统会依次调用所有监听器
