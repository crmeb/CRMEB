# 编码克制规范

> 适用范围：后端、管理端、移动端。与「安全红线」「接口校验」「异常必须处理」不冲突——本规范约束的是**多余**的防御、抽象与拆分，不削弱必要的安全与入口校验。

## 一、防过度防御（强制）

1. **几乎不会发生的边界 / 并发问题，禁止私自加防御代码。**
2. 若认为有必要加：先说明**出错概率**与**预计增加的代码量**，**经同意后再加**。
3. 禁止「以防万一」式空判断、双重加锁、重复状态机校验等冗余逻辑；真实线上风险（支付、库存、资金、鉴权）按既有安全/业务规范处理，不在此列。

## 二、入口单次校验（强制）

4. **外部数据只在入口层校验一次**（Controller / Validate / 请求边界）；通过后，内部靠类型与约定保证格式。
5. **禁止** Service / Dao / 工具函数各层反复判空、反复做同类防御性检查、反复转型同一入参。
6. 内部函数假定调用方已满足契约；契约未满足应视为编程错误（或入口漏检），而不是在深处再补一套校验。

> 与 [接口与响应规范.md](接口与响应规范.md)「所有入参必须校验」一致：校验在入口做全，不是不做，也不是层层做。

## 三、拒绝提前抽象（强制）

7. **只用一次的逻辑直接写在原处**，禁止为「以后可能复用」拆出无调用方的辅助函数 / 工具类 / Trait。
8. 出现**第二次及以上**真实复用、或同一段逻辑已明显阻碍阅读时，再抽取；抽取时保持命名与职责单一，禁止空壳包装。

## 四、控制复杂度（强制）

9. **非必要不滥用 try/catch**：仅在有明确降级、资源清理、或必须吞并转义的边界使用；禁止用大段 try/catch 代替前置条件与正常控制流。空 catch、无差别吞异常仍按 [日志与异常规范.md](日志与异常规范.md) 禁止。
10. **能在一个函数里写清楚的逻辑，不要强行拆成多个函数**；拆分仅用于：职责已独立、复用已成立、或单函数明显过长且可读性下降。
11. 禁止为「看起来分层更细」而制造仅被调用一次、且无独立语义的私有方法链。

## 五、违规判定（简表）

| 行为 | 判定 |
| --- | --- |
| 未经同意为极低概率边界堆防御代码 | ❌ |
| 入口已 Validate，Service/Dao 再重复同条件判空 | ❌ |
| 单次使用的逻辑拆成独立 helper | ❌ |
| 可用 if/early-return 却包一层无意义 try/catch | ❌ |
| 为凑「小函数」把连贯逻辑拆成无语义碎片 | ❌ |
| 入口完整校验 + 内部按类型推进；必要抽象有 ≥2 处复用 | ✅ |
