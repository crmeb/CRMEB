# CRMEB v8 项目说明

> 核对日期：2026-09-17。适用于当前首版开发代码；不代表实际站点已安装或已验收所有能力。

## 1. 项目定位

CRMEB v8 是一套多端电商与客户运营系统。它以商品、用户、订单、支付和售后为基础能力，通过可安装模块扩展产品类型、交易玩法、用户渠道、营销活动、客服和第三方开放接口。

系统不是单一网页商城，而是由以下部分共同组成：

- 运营管理后台：供管理员配置商城、商品、订单、会员、营销和系统能力。
- 用户商城：一套 uni-app 源码面向 H5、微信小程序及 App 等终端。
- 服务端 API：管理端 API、用户端 API、模块 API 与对外开放 API。
- 异步与实时服务：Redis 队列、定时任务、Workerman WebSocket 网关。
- 插件与驱动：业务模块按安装状态加载，支付、存储、短信等第三方能力按驱动扩展。

## 2. 适用场景

从当前代码实现看，系统适合以下场景：

- 实物电商：商品分类、SKU、购物车、优惠券、订单、物流、门店自提、评价与售后。
- 数字商品：网盘资源、卡密等支付后自动履约的商品。
- 本地生活：门店核销等相关业务。
- 会员运营：会员卡、会员权益、等级、余额、积分、签到、抽奖和新人礼。
- 社交营销：分销代理、砍价、拼团、秒杀、渠道码和公众号运营。
- 多渠道经营：H5、App、微信小程序、微信公众号。
- 企业集成：对外 API 账号、权限控制、推送任务以及 MCP 协议入口。

是否能够直接投入某一行业生产使用，还取决于对应模块是否已经安装启用、支付/消息/存储驱动是否配置，以及业务规则是否完成验收。

## 4. 核心业务对象

### 4.1 商品

商品由“商品中台主记录 + 产品类型扩展”构成：

- `eb_product_center` 存放跨产品类型共享的信息。
- 产品类型模块保存自身扩展字段、SKU 和履约数据。
- 当前产品类型包括实物、网盘和卡密。
- `product_type` 决定库存、履约、物流、详情扩展和售后规则。

### 4.2 交易模式

交易模式回答“商品怎么卖”，与产品类型相互独立：

- 普通购买和会员交易模式由核心应用注册。
- 砍价、拼团、积分商城、秒杀由交易模块注册。
- 交易模式负责活动定价、下单校验、支付前后钩子和生命周期规则。

“卡密”是产品类型，“秒杀”是交易模式；二者理论上是两个维度。代码中的兼容性声明目前主要用于约定，新增组合仍需在选品和下单阶段完成业务验证。

### 4.3 订单中台

`eb_order_center` 是多订单类型的统一汇总入口，关联 `eb_order_item` 商品快照和 `eb_order_log` 状态日志。具体产品类型或独立交易模式可保留自己的订单扩展表，再通过订单类型适配器统一输出：

- 状态树与展示状态；
- 支付状态；
- 可操作按钮；
- 订单进度；
- 列表和详情扩展数据。

### 4.4 售后与退款

售后申请使用 `eb_after_sale` 和 `eb_after_sale_item`，资金退款使用 `eb_refund_order`。产品类型通过售后规则注册中心声明可用售后类型、时限和处理规则，退款副作用通过 `eb_refund_effect` 记录以支持幂等处理。

### 4.5 用户与资产

用户主数据以 `eb_user` 为中心，并关联：

- 地址、标签、分组、等级和会员；
- 余额、积分、佣金及对应账单；
- 收藏、浏览、搜索和访问行为；
- 推广关系、分销身份和提现记录；
- 优惠券、发票、站内信和消息阅读状态。

### 4.6 模块与驱动

模块和驱动是两类不同扩展：

- 模块扩展业务规则、路由、控制器、数据表、菜单和前端页面。
- 驱动对接支付、上传、短信、邮件、物流、打印、机器人、采集和发票服务商。

模块或驱动目录存在不等于运行时生效。具有 `plugin.json` 的扩展通常还要在 `eb_module_install_log` 中满足 `status=1` 且 `enabled=1`。

## 5. 系统入口

| URL/进程 | 用途 | 备注 |
|---|---|---|
| `/admin` | 管理端单页应用 | 静态页面入口，不是管理 API 前缀 |
| `/adminapi/*` | 管理端 API | JWT/缓存令牌 + 角色权限 |
| `/api/*` | 用户端 API | 支持游客态与强制登录接口 |
| `/api/v2/*` | 部分用户端 v2 API | 与 v1 路由并存 |
| `/api/outapi/*` | 对外开放 API | `appid/appsecret` 换取访问令牌 |
| `/adminapi/kefu/*` | 客服工作台与游客咨询 | 客服请求选择独立客服 token，游客组按路由免登录 |
| `/ws?service=...` | WebSocket 统一入口 | 由 Nginx 转发到 Workerman `40001` |
| `php think queue:listen --queue` | Redis 队列消费者 | 必须由守护进程托管 |
| `php think timer start --d` | 定时任务进程 | 执行系统和模块定时任务 |
| `php think workerman start --d` | 长连接进程 | 后台通知、客服聊天等 |

## 7. 技术栈摘要

### 7.1 服务端

| 能力 | 主要实现 |
|---|---|
| Web 框架 | ThinkPHP 8、think-multi-app |
| ORM/数据访问 | ThinkPHP ORM + Model/DAO/Services 分层 |
| 数据库 | MySQL 8、`utf8mb4`、默认表前缀 `eb_` |
| 缓存 | 文件缓存或 Redis，生产建议 Redis |
| 队列 | `topthink/think-queue`，默认 Redis 连接 |
| 实时通信 | Workerman + Channel，统一 WebSocket 网关 |
| 认证 | JWT + 缓存中的令牌状态，自定义/标准认证头兼容 |
| 文件 | 本地公开盘及阿里、腾讯、七牛、华为、京东、天翼等驱动 |
| 支付 | 微信支付、微信支付 V3、支付宝、通联支付驱动 |
| 消息 | 站内信、短信、邮件、公众号/小程序消息、机器人渠道 |
| 数据导入导出 | PhpSpreadsheet、前端 ExcelJS/xlsx |

### 7.2 管理端

- Vue 3.5、Vue Router 4、Pinia 2。
- Element Plus 2.9、vxe-table 4、ECharts 5。
- Vite 5 构建，Node.js >=18、npm >=7，实际依赖版本以锁文件为准。
- Axios 请求 `/adminapi`，认证头为 `Authori-zation: Bearer <token>`。
- 前端路径前缀 `/admin`，history 路由模式。
- 后台菜单来自服务端权限数据，静态路由与插件 UMD 扩展共同参与页面装载。

### 7.3 用户端

- uni-app 工程，代码中包含 H5、小程序和 App 条件编译。
- `manifest.json` 声明微信/支付宝/百度/头条小程序及 App 配置。
- 用户请求统一访问 `{HTTP_REQUEST_URL}/api/{path}`。
- 通过 `Form-type` 区分 `h5`、`routine`、`app` 等渠道。
- 工程根目录有 `package.json`、`vite.config.js` 和锁文件，使用 uni-app 官方 CLI。
- 页面、API、配置、`pages.json` 和 `manifest.json` 均位于 `src/`。

## 8. 快速开始

### 8.1 宿主机开发环境（默认）

前置条件：PHP 8.2-8.4、Composer 2、MySQL 8 和 Redis。数据服务连接以 `backend/.env` 为准，不默认假定 Docker 容器名或映射端口。

日常启动使用：

```bash
cd backend
composer install
php think run --host 127.0.0.1 --port 8011
```

默认访问地址：`http://localhost:8011`。

首次初始化见 [开发指南](开发指南.md)。

### 8.2 Docker Compose（可选）

只有明确选择容器环境时使用：

```bash
./run.sh start
./run.sh ps
./run.sh logs
```

Docker 环境要求本机端口 `8011`、`33061`、`63791`、`40001` 未冲突。`./run.sh install` 会要求确认并清理已有运行数据，不作为日常启动命令。

### 8.3 管理端源码开发

```bash
cd frontend/admin
npm ci
npm run dev
```

开发服务器默认端口为 `1619`，并把 `/adminapi` 代理到 `http://localhost:8011`。

前端各端也可用仓库根 `run.sh` 一键执行（`node_modules` 缺失时自动 `npm install`）：

| 命令 | 作用 |
|---|---|
| `./run.sh admin:dev` | 管理端开发测试启动（端口 `1619`），等价 `npm run dev` |
| `./run.sh admin:build` | 管理端 `build:all`（主包 + 扩展 UMD）并发布到 `backend/public/admin` |
| `./run.sh uni:dev` | 用户端 H5 开发测试启动，等价 `npm run dev:h5` |
| `./run.sh uni:build` | 用户端 H5 构建并发布到 `backend/public`（PHP 侧文件不受影响） |

交互式菜单（直接执行 `./run.sh`）对应编号为 `11/12/21/22`。

### 8.4 后台进程

```bash
cd backend
php think queue:listen --queue
php think timer start --d
php think workerman start --d
```

宿主机环境按任务需要启动上述进程。若明确使用根 Compose，则已由独立的 `queue`、`timer`、`workerman` 服务托管，不要重复启动消费者或网关；两种环境都仍需检查服务健康和业务队列开关。

## 9. 关键配置

后端配置以 `backend/.env` 和 `backend/config/*.php` 为主，常用配置域包括：

- `APP`：主机、时区、应用密钥。
- `DATABASE`：MySQL 地址、端口、数据库、账号、字符集、表前缀。
- `CACHE`/`REDIS`：缓存驱动、Redis 地址、密码、库号与前缀。
- `QUEUE`：队列命名前缀。
- `FILESYSTEM`：文件盘与上传驱动。
- 支付、短信、邮件、打印、物流等业务配置：通常由后台驱动配置和数据库记录管理。

前端配置主要位于：

- `frontend/admin/src/setting.js`：管理 API 地址和路由前缀。
- `frontend/admin/vite.config.js`：开发代理、构建目录和 `/admin` 部署前缀。
- `frontend/uni-app/src/config/app.js`：用户端请求域名、认证头和请求超时；API 域名由 `UNI_APP_API_URL` 注入。
- `frontend/uni-app/src/manifest.json`：各端应用标识、权限和 SDK 配置。

所有真实密钥都应按环境注入或在受控后台中配置，不能提交到版本库。详见[安全与配置](安全与配置.md)。

## 10. 已知边界与维护提示

- 插件启用状态依赖数据库，静态阅读目录不能判断生产实际开启了哪些功能。
- 当前可发现 22 个模块、30 个驱动（必装 1 + 默认 6、默认安装 15）；新装默认安装 7 个模块和 15 个驱动，详见 [模块说明](模块与驱动.md)。安装不等于第三方服务已配置可用。
- 基础安装 SQL 与模块 Installer 共同定义首版新装结构。仓库保留历史升级设施，但不把历史 SQL 当作新装必跑步骤。
- 管理端和用户端存在较多历史兼容路由，新增能力应优先使用现有中台、注册中心和模块规范。
- API 业务状态主要在 JSON 的 `status` 字段中表达，不能只依赖 HTTP 状态码判断成功失败。
- 仓库已有支付、退款、存储、打印和签到专项回归脚本，但不等于完整的端到端覆盖，见 [开发指南](开发指南.md)。
- `run.sh install` 和 `run.sh delete` 会清理数据库持久化目录、日志及运行目录，只能用于确认可丢弃数据的环境。

## 11. 术语表

| 术语 | 含义 |
|---|---|
| 管理端 | Vue 管理后台页面，URL 通常以 `/admin` 开头 |
| AdminAPI | 管理后台调用的后端 API，URL 以 `/adminapi` 开头 |
| 用户端/C 端 | uni-app 构建的 H5、小程序或 App |
| 产品类型 | 商品的业务形态和履约规则，例如实物、卡密 |
| 交易模式 | 商品的售卖方式，例如普通、秒杀、拼团 |
| 订单中台 | 统一聚合不同来源订单的查询、状态和操作能力 |
| 模块 | 带业务逻辑、路由、表和菜单的可插拔扩展 |
| 驱动 | 对接某类第三方供应商的实现，例如某支付或存储服务 |
| Installer | 模块/驱动的安装、卸载、启用和禁用生命周期实现 |
| Registry | 运行时注册中心，根据 key 找到某类处理器 |
| source_type | 订单中台用于识别订单来源/适配器的类型标识 |
| Form-type | 用户端请求头中的渠道标识，例如 `h5`、`routine`、`app` |
