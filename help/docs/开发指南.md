# 开发指南

> 核对日期：2026-09-17。默认在仓库根目录开始操作，并优先使用宿主机环境；涉及数据库安装、卸载或真实外部服务时需另行确认。

## 1. 环境要求

### 1.1 后端

`backend/composer.json` 的实际约束为：

| 依赖 | 要求 |
|---|---|
| PHP | `>=8.2 <8.5` |
| MySQL | 8.0 |
| Redis | 建议使用；队列和并发锁依赖 Redis |
| Composer | 可安装 Composer 2 |
| PHP 扩展 | JSON、cURL、BCMath、Mbstring、Zip、SimpleXML 等 |

根 README 的历史最低版本说明不能替代 Composer 约束，应以 `>=8.2 <8.5` 为开发环境基准。

### 1.2 管理端

| 依赖 | 要求 |
|---|---|
| Node.js | `>=18` |
| npm | `>=7` |
| 框架 | Vue 3.5 + Vue Router 4 + Pinia 2 + Element Plus 2.9 |
| 构建 | Vite 5，使用 `package-lock.json` 安装依赖 |

团队应固定经构建验证的 Node LTS 版本，使用 `npm ci` 复现锁定依赖，不再按 Vue CLI/Webpack 工程运行。

### 1.3 用户端

`frontend/uni-app` 是 uni-app 官方 CLI 工程，根目录包含 `package.json`、锁文件和 `vite.config.js`，源码在 `src/`。使用 Node.js >=18；小程序需对应开发者工具，App 还需目标平台打包与真机环境。

## 2. 获取与初始化

### 2.1 不覆盖本地配置

仓库中的以下路径包含运行时或本地状态：

- `backend/.env`、`backend/.constant`；
- `backend/runtime/`；
- `backend/public/uploads/`；
- `docker/mysql/`；
- `frontend/admin/node_modules/` 和构建产物。

切换分支或拉取代码前先检查 `git status`，不要覆盖其他开发者或本机已有配置。

### 2.2 宿主机初始化（默认）

安装后端依赖：

```bash
cd backend
composer install
```

然后配置 `backend/.env`，在宿主机启动 MySQL 8 和 Redis，并通过安装向导或安装 SQL 初始化数据库。Web 服务根目录应指向 `backend/public`，并确保 `runtime` 和上传目录对 PHP 进程可写。开发期可直接使用 `php think run --host 127.0.0.1 --port 8011`。

宿主机开发常见端口：

| 服务 | 地址 |
|---|---|
| Web/ThinkPHP | `http://localhost:8011` |
| MySQL | 以 `backend/.env` 为准，通常为 `127.0.0.1:3306` |
| Redis | 以 `backend/.env` 为准，通常为 `127.0.0.1:6379` |
| WebSocket | `ws://localhost:40001` 或经 `/ws` 代理 |

### 2.3 Docker Compose（可选）

只有用户明确选择 Docker，或当前目标实例已运行在根 Compose 中时，才使用：

```bash
./run.sh start
./run.sh ps
```

容器映射地址为 Web `http://localhost:8011`、MySQL `127.0.0.1:33061`、Redis `127.0.0.1:63791`。根 Compose 同时托管 `queue`、`timer`、`workerman`；容器运行不代表队列开关与第三方配置已启用。

首次且可丢弃数据时才使用 `./run.sh install`，它会交互确认并清理当前 Docker MySQL 数据、运行目录和日志。本文档更新或静态检查不需要执行安装。

## 3. 日常启动

### 3.1 后端 HTTP

默认从宿主机启动 ThinkPHP 开发服务：

```bash
cd backend
php think run --host 127.0.0.1 --port 8011
```

需要验证 URL 重写、静态资源、上传或 WebSocket 时，应在实际目标的 Nginx/进程守护环境再做回归。若本次明确选择 Docker，则改用 `./run.sh start`。

### 3.2 管理端

```bash
cd frontend/admin
npm ci
npm run dev
```

- 开发端口：`1619`。
- Vite `base` 与页面路由前缀：`/admin`；端口占用时以终端实际地址为准。
- `/adminapi` 自动代理至 `http://localhost:8011`。
- 启动脚本还会执行 `src/libs/start.js` 的初始化逻辑。

生产构建：

```bash
npm run build
```

插件扩展构建：

```bash
npm run build:ext
npm run build:all
```

`build:ext` 构建可由管理端动态加载的扩展包；修改插件页面后不能只构建主应用。

仓库根 `./run.sh admin:dev` / `./run.sh admin:build` 是上述 `dev` 与 `build:all` + 发布的一键封装；后者清空 `backend/public/admin` 后写入新产物。

### 3.3 用户端

```bash
cd frontend/uni-app
npm ci
npm run dev:h5
```

通过未入库的 `.env.development.local` 配置 `UNI_APP_API_URL`（只填域名和端口，不包含 `/api`）。生产独立域名可使用 `.env.production.local`，不要改写共享环境默认值。H5 同源部署可留空，小程序/App 必须明确配置可访问的后端地址。

其他目标平台：

```bash
npm run dev:mp-weixin
npm run build:mp-weixin
npm run build:h5
npm run build:mp-alipay
npm run build:app
```

平台标识与权限位于 `src/manifest.json`，页面注册位于 `src/pages.json`。产物在 `dist/{dev,build}/{platform}`，小程序使用对应开发者工具打开目标目录，并检查条件编译后的 `Form-type`。

仓库根 `./run.sh uni:dev` / `./run.sh uni:build` 是 H5 `dev:h5` / `build:h5` 的一键封装；发布时清理 `backend/public/{assets,pages,static}` 后覆盖拷贝 `dist/build/h5`，再访问 `http://localhost:8011`。

不要把生产 AppSecret、证书或私钥写入前端工程；前端代码和小程序包对用户可见。

### 3.4 后台进程

宿主机环境按需启动以下进程。任务不需要时不应自动启动；明确使用根 Compose 时则由对应容器管理，避免重复启动。队列配置和守护方式见 [部署指南](部署指南.md)。

```bash
cd backend
php think queue:listen --queue
php think timer start --d
php think workerman start --d
```

停止或重启：

```bash
php think timer stop
php think timer restart
php think workerman stop
php think workerman restart
```

开发环境修改事件、模块注册、队列任务或 Workerman 处理器后，应重启对应长驻进程。

## 4. 配置说明

### 4.1 后端环境变量

常用配置：

```ini
APP_DEBUG = true

[APP]
DEFAULT_TIMEZONE = Asia/Shanghai
APP_KEY = local-only-key

[DATABASE]
TYPE = mysql
HOSTNAME = 127.0.0.1
HOSTPORT = 3306
DATABASE = crmeb
USERNAME = crmeb
PASSWORD = change-me
PREFIX = eb_
CHARSET = utf8mb4
DEBUG = true

[CACHE]
DRIVER = redis
CACHE_PREFIX = crmeb_dev:
CACHE_TAG_PREFIX = crmeb_dev_tag:

[REDIS]
REDIS_HOSTNAME = 127.0.0.1
PORT = 6379
REDIS_PASSWORD =
SELECT = 0

[QUEUE]
QUEUE_NAME = _dev
```

不同开发环境必须使用不同的缓存前缀和队列名，避免共享 Redis 时互相消费任务或污染登录状态。

### 4.2 管理端配置

`frontend/admin/src/setting.js` 与 Vite 环境变量：

- `VITE_APP_API_URL` 覆盖 `apiBaseURL`，默认 `${location.origin}/adminapi`；
- `VITE_APP_H5_URL` 设置独立 H5 商城地址，留空为同源；
- `routePre` 为 `/admin`；
- 路由模式为 `history`。

`frontend/admin/vite.config.js`：

- 开发代理 `/adminapi -> http://localhost:8011`；
- 输出目录 `dist`；
- 静态资源目录 `system_static`；
- 开发期挂载 `dist/static/extensions`，生产主包不包含扩展开发加载器。
- 扩展构建入口是 `scripts/build-extensions.js`，插件资源复用宿主 Vue/Element Plus 环境。

### 4.3 用户端配置

`frontend/uni-app/src/config/app.js`：

- `HTTP_REQUEST_URL`：请求域名，不含 `/api`；
- `TOKENNAME`：默认 `Authori-zation`；
- `HEADER.Form-type`：由条件编译设置渠道；
- `LIMIT`：默认分页数；
- `TIMEOUT`：请求超时，当前实际值为 `100000` 毫秒（100 秒），不要按旧注释中的 10 秒理解。

## 5. 后端开发规范

### 5.1 分层职责

| 层 | 应做 | 不应做 |
|---|---|---|
| Controller | 读取请求、校验、调用 Service、返回响应 | 复杂 SQL、大事务、跨领域规则 |
| Validate | 参数格式、必填、范围和场景校验 | 数据库业务编排 |
| Services | 业务规则、事务、数据组合、事件/队列调度 | 输出页面或依赖具体 HTTP 响应 |
| DAO | 查询条件、分页、聚合和持久化封装 | 业务流程和用户提示文案 |
| Model | 表、字段转换、搜索器和关联 | 跨多个领域的业务编排 |
| Listener | 处理事件扩展 | 无幂等保护的关键资金写入 |
| Jobs | 可重试异步工作 | 假设只执行一次 |

### 5.2 请求与响应

请求参数使用项目 `Request` 的 `getMore`、`postMore` 等能力统一获取。响应使用：

```php
return app('json')->success('操作成功', $data);
return app('json')->fail('操作失败', $context);
```

成功响应业务状态为 200，失败一般为 400；认证、维护等场景还会有 401/402/403 等业务状态。接口调用方应读取 JSON `status`。

### 5.3 数据访问

- 常规业务统一走 Model/DAO，不在 Service 和 Controller 中散落 `Db::table()`。
- Installer 的 DDL/DML 是允许直接使用 Db 的特殊生命周期场景。
- 查询列表遵循 `page`/`limit`，单页最大 100。
- 金额计算使用高精度方式。
- 事务内只包含必须原子提交的数据库操作，避免网络调用长时间占锁。

### 5.4 异常

- 按端和场景使用已有异常类型，如 `ApiException`、`AdminException`、`AuthException`。
- 给用户的消息可操作、不过度暴露内部信息。
- 日志记录业务单号、用户/管理员 ID、模块 key 和供应商请求 ID。
- 不吞掉关键异常；允许降级的钩子也应记录结构化错误。

### 5.5 事件

- 事件名使用稳定的大驼峰业务语义，例如 `OrderCreateAfter`。
- 事件参数应有明确结构，跨模块修改前搜索全部触发方与监听器。
- 监听器必须考虑重复触发和部分失败。
- 观察型营销模块通过事件接入，不直接改核心下单代码。

### 5.6 队列

- 任务参数使用稳定业务 ID，不序列化庞大或易过期模型对象。
- 消费时重新读取当前业务状态。
- 先判断是否已完成，再执行副作用。
- 失败可重试，超过阈值进入失败队列/日志并支持人工补偿。

## 6. API 开发

### 6.1 路由位置

| API | 路由目录 |
|---|---|
| 管理端核心 | `backend/app/adminapi/route/*.php` |
| 用户端核心 | `backend/app/api/route/*.php` |
| 模块管理端 | `backend/modules/**/route/admin.php` |
| 模块用户端 | `backend/modules/**/route/user.php` |

### 6.2 新增路由检查

- 使用明确 HTTP 方法。
- 路由路径与现有业务域一致。
- 添加 `real_name`，方便权限和接口管理。
- 正确选择无认证、可选认证或强制认证。
- 管理端写操作经过管理员认证、角色和日志中间件。
- 防重复提交接口评估 `BlockerMiddleware`。
- 插件接口放插件路由文件，不写进核心路由。
- 同步前端 API 封装和相关文档。

## 7. 管理端开发规范

### 7.1 目录

- 页面放 `src/pages/{domain}`。
- API 按业务域放 `src/api`。
- 通用组件放 `src/components`，领域私有组件放页面目录内。
- 静态路由映射放 `src/router/modules`。
- 全局状态放 `src/store/module`，使用 Pinia `useXxxStore()`，局部页面状态优先留在组件。

### 7.2 请求

统一复用 `src/libs/request.js` 的 Axios 实例，以自动获得：

- `/adminapi` baseURL；
- token 请求头；
- 登录过期处理；
- 错误消息处理；
- 客服工作台请求选择 `kefu_token`，URL 仍走 `/adminapi`。

不要为普通页面创建绕开主请求实例的 Axios 客户端。

### 7.3 路由与菜单

管理端页面可访问通常同时依赖：

1. 前端存在可解析的组件/静态路由；
2. 后台 `eb_system_menus` 返回对应菜单和权限；
3. 当前管理员角色拥有接口权限；
4. 模块已启用且扩展资源已部署。

只加前端路由或只插入菜单都会造成半成品状态。

### 7.4 插件页面

插件页面支持扩展 UMD 包。修改后执行：

```bash
npm run build:ext -- --ext <key>
```

页面容器、菜单路径、扩展名和产物 URL 必须一致；发布时检查缓存和静态资源返回的 Content-Type。开发期扩展源码可通过加载器即时 HMR，不必每次重建 UMD；正式部署仍需构建和发布资源。

## 8. uni-app 开发规范

- 新页面先判断应放主包还是分包，控制小程序主包体积。
- 在 `pages.json` 注册完整路径和导航配置。
- 请求统一使用 `src/utils/request.js`。
- 需要登录的接口不要错误传 `noAuth=true`。
- 新渠道差异使用条件编译，不在运行时散落大量平台判断。
- H5 history 路由需要服务器 fallback 到用户端入口。
- 微信支付、登录、定位、订阅消息等真机行为不能仅用 H5 模拟验收。
- 更新隐私权限时同步小程序后台、App 隐私描述和文档。

## 9. 插件开发

先阅读[模块说明](模块与驱动.md)。简要流程：

1. 判断需求属于 product、trade、marketing、channel、service 还是 driver。
2. 建立 `plugin.json`、`App.php`、`Installer.php` 和标准目录。
3. 通过注册中心/事件接入，不修改核心分支硬编码模块 key。
4. Installer 创建表、菜单和种子，保持幂等。
5. 添加 admin/user 路由和权限。
6. 完成前端页面或通用动态扩展。
7. 验证安装、启用、禁用、重启长驻进程和卸载。

## 10. 数据库变更

当前处于首版开发阶段，核心表变更更新新装 SQL、Model/DAO/Services 与 [数据库设计](数据库设计.md)；插件自有表、菜单与种子更新 Installer。插件版本统一为 `1.0.0`，不新建旧站点迁移或版本递增。

首次和重复安装仍需幂等，自定义表前缀与卸载资源边界仍需验证。仓库已有历史迁移文件不代表本次变更需要逐个执行；未来明确维护存量站点时，再评估已有表补列、数据回填和增量升级。

## 11. 检查与测试

### 11.1 静态/一致性命令

```bash
cd backend
php think plugin:manifest-check
php think plugin:required-check
php think event:check
php think registry:check
php think channel:menu-check
```

```bash
cd frontend/admin
npx eslint path/to/changed-file.vue path/to/changed-file.js
npm run build
```

注意：`npm run eslint` 带 `--fix`，会修改文件；只想检查时应确认团队脚本或直接运行不带 fix 的 ESLint 命令。

### 11.2 当前测试现状

测试脚本按端存放；仓库根 `tests` 目录是本地测试登记处（可缺失，不随仓库分发），存在时以其中索引为准。管理端和用户端测试位于各自 `scripts/`。按改动选用对应脚本，执行前先确认依赖和写入范围。有专项脚本不等于具备统一 PHPUnit 配置或完整端到端覆盖，实际执行结果应由具体业务变更另行记录。

建议优先补充：

- 价格计算与优惠分摊单元测试；
- 订单创建、支付回调、取消和退款集成测试；
- 各产品类型/交易模式契约测试；
- 模块 Installer 幂等和卸载边界测试；
- 管理端权限和对外 API 越权测试；
- 队列重复消费与定时任务幂等测试。

### 11.3 最小手工回归

每次业务改动至少执行：

1. 管理员登录与菜单加载。
2. 目标 API 正常、未登录和无权限场景。
3. 新建/编辑目标业务数据。
4. 用户端目标页面在至少一个真实目标平台运行。
5. 队列、定时器或 WebSocket 相关改动重启进程后验证。
6. 检查 `backend/runtime/log` 和浏览器控制台。

## 12. 提交前检查清单

- `git diff` 中没有 `.env`、密钥、构建缓存或用户上传数据。
- 没有覆盖他人的未提交改动。
- 新路由有认证、权限、日志和 `real_name`。
- 新数据表/字段覆盖首版新装与插件首次、重复安装；旧站点升级仅在明确进入维护阶段时要求。
- 金额、库存、回调和异步任务已考虑幂等。
- 插件清单、Installer、菜单、路由和前端页面一致。
- 文档和实际命令/路径一致。
- 已记录无法运行的测试及剩余风险。

开发入口是根 `AGENTS.md`，规则与技能真源位于 `.crmeb/`。VS Code 的 `.vscode/` 属于可选本地配置，不影响项目启动，也不需要为了读取规则重新创建其他工具目录。
