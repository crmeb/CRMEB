# 运维手册

> 核对日期：2026-09-14。本文是检查与排障手册，不授权清库、退款、补偿或批量重放。

## 1. 日常检查

建议每日或由监控自动检查：

| 项目 | 检查内容 |
|---|---|
| HTTP | 首页、`/admin`、一个只读 API 的可用性与延迟 |
| PHP | PHP-FPM 进程、错误率、慢请求、内存和进程池 |
| MySQL | 连接数、慢查询、锁等待、磁盘、复制和备份 |
| Redis | 内存、连接、命中率、驱逐、持久化和延迟 |
| 队列 | 消费者数量、积压、失败任务、最老任务年龄 |
| Timer | 进程状态、最近成功/失败任务和运行耗时 |
| Workerman | 网关进程、连接数、断连率和内部 Channel |
| 存储 | 上传成功率、磁盘/Bucket 容量、CDN 回源 |
| 外部服务 | 支付、短信、微信、物流等错误率和余额/额度 |

## 2. 服务管理

### 2.1 Docker

```bash
./run.sh ps
./run.sh logs
./run.sh restart
./run.sh stop
```

不要在生产使用 `install` 或 `delete`，两者会清理数据目录。

根 Compose 已包含 `crmeb_queue`、`crmeb_timer`、`crmeb_workerman`；优先通过对应服务管理，避免同时在宿主机重复启动。下方 PHP 启停命令用于非 Compose 环境。

### 2.2 队列

启动：

```bash
cd backend
php think queue:listen --queue
```

排障顺序：

1. 检查消费者进程是否存在。
2. 检查 Redis 连接和队列前缀是否正确。
3. 检查 PHP 日志和失败任务表。
4. 用业务单号确认任务是否已经成功执行，避免盲目重放。
5. 修复原因后按幂等保证重试。

Compose 队列心跳写入 `backend/runtime/.queue_heartbeat`，只能证明包装脚本观察到消费者存活，不能代替业务消费成功检查。异步队列需要 `queue_open=1` 与 Redis 缓存；延迟取消配置、队列后缀和守护方式见 [部署指南](部署指南.md)。

### 2.3 Timer

```bash
php think timer start --d
php think timer stop
php think timer restart
```

PID 文件位于 `backend/runtime/timer.pid`。排查“自动收货/订单取消不执行”时，不仅检查进程，还要检查 `eb_system_crontab` 配置、任务启用状态、模块状态和任务日志。

### 2.4 Workerman

```bash
php think workerman start --d
php think workerman stop
php think workerman restart
```

PID 文件位于 `backend/runtime/workerman.pid`。排查实时通知：

1. 浏览器是否成功连接 `/ws?service=...`。
2. Nginx 是否返回 `101 Switching Protocols`。
3. `40001` 网关是否监听。
4. 请求的 service 是否已注册。
5. 内部 `127.0.0.1:40003` Channel 通信是否正常。
6. 代理超时、负载均衡和 TLS 是否正确。

## 3. 日志

主要日志位于 `backend/runtime/log`，具体目录由 ThinkPHP 日志配置决定。容器 Nginx 日志位于 Compose 映射的 `docker/nginx/log`。

日志应至少包含：

- 请求/任务时间与级别；
- 业务单号、订单号、退款号；
- 用户/管理员/对外账号 ID；
- 模块 key、驱动类别与供应商请求 ID；
- 错误类型、堆栈和重试次数。

日志不得包含：

- 数据库、Redis 密码；
- AppSecret、私钥、完整 JWT；
- 支付证书内容；
- 完整银行卡、身份证号或不必要的个人信息。

建立日志轮转，防止 `runtime` 或 Nginx 日志占满磁盘。

## 4. 常见故障

### 4.1 页面能打开但 API 404

- 确认请求前缀：管理 API 是 `/adminapi`，用户 API 是 `/api`。
- 检查 Nginx 重写是否进入 `index.php`。
- 检查模块是否安装并启用。
- 搜索对应 `route/*.php`，确认 HTTP 方法和完整 group 前缀。
- 清理路由/应用缓存并重启 PHP 长驻进程。

### 4.2 返回“插件未安装或未启用”

- 检查 `plugin.json` 的 key。
- 检查 `eb_module_install_log` 中相同 key 的 `status=1`、`enabled=1`。
- 检查依赖插件是否启用。
- 在后台重新启用后重启队列、Timer 和 Workerman。

### 4.3 登录频繁失效

- 检查客户端是否发送 `Authori-zation: Bearer ...`。
- 检查 Redis 是否重启、淘汰或连接到错误库号。
- 检查多实例是否使用一致的 `APP_KEY`、JWT 配置和缓存。
- 检查缓存前缀是否被其他环境共用。
- 检查服务器时间和时区。

### 4.4 重复订单/重复扣减

- 检查客户端是否重复提交。
- 检查 `BlockerMiddleware` 是否因文件缓存模式被绕过。
- 检查业务唯一键、数据库唯一索引和事务条件更新。
- 检查支付回调、队列重试和定时任务是否幂等。
- 先冻结自动补偿，按业务单号核对订单、库存和账单后处理。

### 4.5 支付成功但订单未更新

- 检查支付平台回调地址和公网可达性。
- 检查签名、证书、商户号和支付驱动配置。
- 用外部交易号查询 `eb_order_center`、具体订单和支付日志。
- 确认回调返回格式符合支付平台要求，避免持续重试。
- 检查支付成功事件或队列后续任务是否失败。
- 不要仅凭客户端支付结果页面手工改订单状态。

微信支付还需按原商户单号核对 `eb_pay_record` 的支付合同、终态、退款意图和后置任务，确认 `paymentRecover` 定时任务及驱动已正确加载。先核对当前安装结构、备份和合同信息，不自行拼接旧商户配置。

`php think pay:recover` 会查询真实商户接口，并可能执行补偿退款、资金及履约恢复，**不是只读检查**；`php think refund:sync` 也可能同步并变更退款状态。执行前需明确业务范围、取得操作授权并在隔离环境演练。客户端成功页不能作为补单依据。

### 4.6 退款状态不一致

- 按退款单号查询 `eb_refund_order`。
- 向支付平台查询真实退款状态。
- 检查 `eb_refund_effect` 中各副作用执行状态。
- 核对售后单和订单中台状态。
- 对失败副作用做幂等重放，避免重复加库存、返佣或退券。

### 4.7 图片上传成功但无法访问

- 检查附件记录和实际存储路径/Bucket key。
- 本地存储检查 `backend/public/uploads` 权限和 Nginx root。
- 对象存储检查域名、Bucket 权限、CORS、防盗链和 HTTPS。
- 多实例检查是否错误使用单机本地存储。

### 4.8 管理端菜单存在但页面空白

- 检查菜单 `menu_path` 与前端路由映射。
- 检查插件扩展 UMD 文件是否发布并返回 200。
- 检查浏览器控制台的 chunk、跨域和 Content-Type 错误。
- 清理入口/插件资源缓存。
- 确认主管理端与插件扩展使用兼容的 Vue 3/Element Plus 和正确 UMD 入口。

## 5. 缓存管理

清缓存前先判断缓存类型和影响：

- 通用配置/页面缓存可重建。
- 登录 token 状态删除会使用户下线。
- Redis 队列不是普通缓存，不能用全库清理方式处理。
- 分布式锁键误删可能放大重复请求风险。

优先使用项目提供的定向缓存命令或后台刷新缓存功能，不执行无范围的 Redis `FLUSHALL`。

## 6. 数据库备份

### 6.1 策略

- 每日全量备份 + 高频增量/binlog。
- 升级、批量导入、插件卸载前执行额外备份。
- 备份加密、异地保存并设置保留周期。
- 定期进行恢复演练，不把“备份任务成功”当作“数据可恢复”。

### 6.2 恢复顺序

1. 隔离写流量和后台任务。
2. 确认要恢复的时间点和受影响业务单号。
3. 准备与备份匹配的代码版本。
4. 恢复数据库和上传资源。
5. 校验数据库版本、模块状态和表结构。
6. 清理可重建缓存，不直接重放全部旧队列。
7. 逐项启动 HTTP、队列、Timer 和 Workerman。
8. 核对订单、支付、退款、库存和资金。

## 7. 插件运维

默认安装与可卸载清单见 [模块说明](模块与驱动.md)。当前首版阶段统一维护 `1.0.0` 的安装定义，不为未发布功能执行历史升级目录。

安装/升级/禁用/卸载前：

- 读取 `plugin.json` 和具体 `Installer.php`。
- 检查依赖和 PHP/CRMEB 版本。
- 备份模块表和共享菜单/配置。
- 记录当前模块安装日志。
- 在预发布环境演练。

操作后：

```bash
cd backend
php think plugin:manifest-check
php think plugin:required-check
php think event:check
php think registry:check
```

并重启所有加载模块代码的长驻进程。

## 8. 容量与性能

AI Agent 与 MCP 额外检查模型凭据有效性、外部调用超时、工具权限、任务运行记录、流式代理缓冲和费用/调用额度。独立 `/api/mcp` 不能使用商城用户 token 或开放平台凭据替代服务密钥。

重点观察：

- `eb_order_center`、`eb_order_item`、账单、日志和访问记录增长。
- 大促时商品详情、活动库存和购物车热点。
- 秒杀库存等热点资源的并发竞争。
- 消息日志、附件、导出文件和海报的存储增长。
- Redis 登录、缓存、锁和队列混用时的内存压力。
- 管理端大列表导出造成的 PHP 内存和 MySQL 长查询。

优化优先级：索引与慢查询 -> 缓存命中 -> 分页/异步导出 -> 队列并发 -> 读写扩展。不要在没有指标的情况下盲目引入复杂基础设施。

## 9. 事故处理原则

1. 先停止扩大影响的写入、回调重试或自动任务。
2. 保留日志、请求 ID、业务单号和数据库现场。
3. 以支付平台、数据库账单和库存记录交叉核对事实。
4. 补偿脚本必须幂等、可审计、可限定业务单号并先在副本验证。
5. 恢复后持续监控，并记录根因、影响、处置和防复发项。
